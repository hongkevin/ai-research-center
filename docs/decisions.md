### D8 — 제품 구조: 공통 엔진 + 표면 2개, 발간 먼저

> ⚠️ **2026-08-05 — [D38](#d38)로 대체됨.** 공통 엔진과 표면 2개 구조는 그대로 유효하다.
> **뒤집힌 것은 "발간 먼저" 하나**다. D8이 검토한 선택지에 *개인 셀프서브 RA 도구*가 없었기 때문이다.

**결정**: 데이터·계산·게이트·서술을 **하나의 엔진**으로 짓고, 그 위에 표면을 둘 올린다. **발간 표면을 먼저** 만든다.

```
                 ┌─────────────────────────────┐
                 │  공통 엔진                   │
                 │  데이터 · 계산 · 게이트 · 서술 │
                 └──────────┬──────────────────┘
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
    ┌───────────────────┐      ┌────────────────────┐
    │ 발간 표면 (지금)    │      │ RA 도구 표면 (보류)  │
    │ 세미오토 자체 발간  │      │ 증권사 내부 도구     │
    │ 무료·일방향        │      │ 유료 seat          │
    │ 인허가 제로        │      │ 영업 필요           │
    └───────────────────┘      └────────────────────┘
```

**근거**:
1. 발간은 **인허가 제로로 당장 시작 가능**하고 유통 경로가 필요 없다 (D5)
2. 7/25 판단 그대로 — *"(b)로 시작하면 발간 실적·골든셋·검증 파이프라인이 자산으로 축적 → 이후 (a) B2B·증권사 제휴·유료화 어느 쪽으로든 전환 가능한 옵션 보존"*
3. [research/02-report-quality.md](research/02-report-quality.md) §3의 **추정 정확도 추적**이 자체 발간에서도 그대로 축적된다. 내 추정 vs 실제 실적 이력이 곧 B2B 전환 시의 신뢰 자산이다
4. RA 인터뷰를 발간 경험을 갖고 가면 질문의 밀도가 다르다

**보류 처리**: RA 도구 표면의 v0 설계는 [surfaces/ra-tool-v0/](surfaces/ra-tool-v0/)에 보존. [research/04-reshape-interview.md](research/04-reshape-interview.md) §7의 가설 H1이 인터뷰로 검증되면 되살린다.

<a id="d9"></a>
### D9 — 목표주가: 엔진은 계산하고, 표면이 정책을 정한다

**충돌이었던 것**: D4는 "단일 목표주가 출력 금지"인데, [research/03-valuation-boundary.md](research/03-valuation-boundary.md)는 "밸류에이션 계산까지 포기한 것은 과잉"이라 결론.

**해소**: 두 층을 분리한다.

| 층 | 정책 |
|---|---|
| **엔진** | 밸류에이션을 **계산한다** — 3표 전개, 멀티플 밴드, 분해 항등식, 시나리오, 교차검증. 모든 입력에 `source` 태그 (`estimate_model` / `human_assumption` / `sec_fact`) |
| **발간 표면** | 단일 목표주가·투자의견 **출력 차단** (D4 유지). 시나리오 3개 + 감도표 + 산식 공개만. G0가 강제 |
| RA 도구 표면 | 계산 제공 + 애널리스트가 명시적으로 채택. 자동 복사 금지 |

즉 **엔진의 능력과 표면의 정책이 다르다.** D4는 발간 표면의 정책으로 유지되고, 엔진은 계산을 온전히 제공한다.

검증된 세부: `PBR = PDR × ROE × 배당성향`은 근사가 아니라 **항등식**이다 (수치 검증 완료). 4개 중 3개를 넣으면 나머지가 결정되므로 정합성을 코드가 강제할 수 있다. 마진 브리지의 `reconciliation` 패턴과 같은 성질.

### D11 — 골든셋 출발점: SMIC 15건 + 선택 효과 보정

7/25가 *"한국어 리포트 품질 벤치마크는 전무하므로 골든셋 자체가 이 프로젝트의 핵심 데이터 자산"*이라 했다. 그 공백의 첫 채움으로 SMIC(서울대 투자 학회) 리포트 15건 분석을 확보했다 ([research/01-benchmark-smic.md](research/01-benchmark-smic.md)).

**다만 그대로 규범으로 쓰면 안 된다.** SMIC는 학회라 **쓰고 싶은 종목을 골라서** 쓴다. 배정 커버리지가 아니다:

| 지표 | 시장 (sell-side) | SMIC 15건 | 해석 |
|---|---|---|---|
| 매수 비중 | 93.1% | 100% | **선택 효과** — 편향이 아님 |
| 내재 상승여력 | 31% | 109.0% | 선택 효과 + 소형주 편중(10건 중 6건 시총 1조 미만). 잔여분 미확인 |

**채택 방식**: 구조는 학습하고 논조는 학습하지 않는다.

| 층 | 판단 |
|---|---|
| 구조 (추정 정밀도, 세그먼트 분해, P·Q 분해, 밸류에이션 논증 사슬, 부록 구성) | ✅ 골든셋으로 사용 |
| 논조·레지스터 (확신 표현, 상승여력 규모, rating 서술) | ❌ 제외 |

**결핍 확인**: 15건 전부가 확신에 찬 매수 아이디어라 **중립·부정 톤 참조가 없다.** 별도 코퍼스가 필요하다.

### D12 — 추정 정확도·revision 추적을 최우선 차별화로 승격

7/25가 이미 *"전 보고서 대비 추정 변화 추적 — 이것이 진짜 차별화"*라 했고, 템플릿 §5에도 반영돼 있다. 7/30~31 분석이 이를 **두 개의 독립 증거로 보강**했다:

| 증거 | 내용 |
|---|---|
| **FnGuide Best Analyst 루브릭** | 100점 중 **40점이 실적 추정 정확도** — 최대 단일 배점. 70%가 검증 가능한 예측 성과 |
| **SMIC 15건 계량** | `추정` 855회, `26E/27E/28E` **15/15건**. 컨센서스 인용은 5/15건뿐 (자체 추정이 표준) |
| 시장 실패 데이터 | 하향 조정이 상향보다 **72일 vs 61일** 지연. 신뢰가 무너지는 지점 |

**추가 결정 — 정합성 표시 3종** ([research/02-report-quality.md](research/02-report-quality.md) §3.5의 C안):

매수 편향 시장에서 rating에 개입하지 않고 **추정·목표주가·rating의 모순만 계산으로 드러낸다.**

| 표시 | 겨냥 |
|---|---|
| 목표주가 ↔ 추정 정합성 (괴리 %) | 근거 없는 목표주가 |
| **revision 정합성** ("추정은 하향, 목표주가는 무변동") | 72일 하향 지연 |
| 상대 대조 (내재 상승여력 vs 시장 평균 31%) | 낙관 편향 자각 |

**매도 의견을 유도하지 않는다.** 93.1% 매수는 발행사 관계·IB·법인영업에서 오는 제도 제약이고(외국계 지점은 같은 시장에서 15~22%), 도구가 고칠 수 없다. 도구는 계산만 하고 판단은 사람이 한다.

**구현 상태**: ✅ Number Registry + G0 구현 완료. 정합성 표시 3종은 미착수 — 추정 레이어가 선행되어야 한다.

### D3 보강 — 리포트는 재무제표에서 출발하지 않는다

SMIC 15건은 두 테마로 배타적으로 갈렸다: **AI 인프라 병목**(10건, `병목` 220회) / **밸류업·지배구조**(5건, `승계` 191회·`배당` 317회). 논리 흐름은:

```
매크로·정책 서사 → 산업 구조(밸류체인·병목) → 종목 선정 → 재무 추정 → 밸류에이션
```

재무 지표는 **논지의 증거**이지 출발점이 아니다. 실증: 손익계산서에서 앵글을 생성하면 NVDA FY2025(매출 폭증)와 TSLA(마진 하락)가 **글자까지 동일한 앵글 3개**를 받는다.

S2(재무분석 → thesis.json) 설계 시 반영할 것 — thesis는 산업·정책 입력을 받아야 한다.

### D14 — S4 서술 모델: GPT-5.6 Luna (최저가 티어)

**실측 근거** (2026-08-01, 삼성전자 FY2025, 5회 반복):

| 지표 | 결과 |
|---|---|
| G0 **1차 통과율** | **100%** (5/5) |
| 숫자 리터럴 유출 | **0%** |
| 카탈로그 밖 키 | 0% |
| 금지어(rating·단정) | 0% |
| JSON 파싱 실패 | 0% |
| 건당 비용 | **$0.0019** |
| 지연 | 9~12초 |

**가장 위험했던 가정이 검증됐다** — "LLM이 숫자 리터럴 없이 쓸 만한 한국어를
만들 수 있는가". 최저가 티어에서 1차 통과율 100%다.

이게 가능한 이유는 Number Registry가 LLM의 역할을 좁혀뒀기 때문이다. 계산도
검증도 하지 않고 정해진 어휘로 문장만 조립하므로, 플래그십이 필요한 작업이
아니다. 비용도 같은 이유로 무의미한 수준이다 — 100건/월에 $0.19.

설계서 추정($0.5~0.9/건)의 **1/300**이다. 추정 당시엔 S1 정규화·S2 분석·
S4 병렬 작성·S5 LLM 검증을 모두 LLM으로 가정했는데, 실제로는 S4만 LLM이고
나머지는 결정론 코드다.

**비용은 이 규모에서 제약이 아니다.** 플래그십(Sol)을 써도 100건/월 $3.45,
코스닥 전종목 분기 갱신도 월 $20 수준이다. 모델 선택은 비용이 아니라 품질로
한다. 다만 G1/G2 LLM 검증을 붙이거나 공시 원문을 프롬프트에 넣으면 이 계산은
깨진다.

<a id="d15"></a>
### D15 — 카탈로그에 방향(부호)을 포함한다

초판은 카탈로그에서 값을 완전히 뺐다. 그랬더니 LLM이 방향을 알 수 없어
모든 문장을 "변동했다"로 썼고, 지표를 하나씩 읊는 읽히지 않는 글이 나왔다.
[research/01-benchmark-smic.md](research/01-benchmark-smic.md) §3이 진단한
"손익계산서에서 출발하면 템플릿이 나온다"가 그대로 재현됐다.

**방향은 크기가 아니다.** 결정적 코드가 부호에서 뽑은 사실이므로 환각이 아니고,
크기는 여전히 노출되지 않는다. 카탈로그에 `direction`(증가/감소/보합)을 넣고
프롬프트에 "정도 표현(크게·소폭·급격히)은 금지"를 추가했다.

결과: 통과율 100%를 유지하면서 문장이 지표를 **연결**하기 시작했다
("원가 부담 완화가 총이익률 개선으로 연결", "영업단의 개선이 순이익단까지").

**남은 한계**: 여전히 산업·정책 서사가 없다. 프롬프트에 재무 카탈로그만 있어
LLM이 쓸 수 있는 것이 재무 기계학뿐이다. 세그먼트·공시 본문·산업 데이터가
붙어야 [research/01](research/01-benchmark-smic.md) §3이 말한 진짜 리포트가
된다. 이건 데이터 레이어 확장 과제이지 모델 문제가 아니다.

<a id="d16"></a>
### D16 — 논지는 결정적 코드가 만들고, LLM은 그것을 글로 만든다

[D15](#d15)가 남긴 한계("재무 기계학에서 멈춘다")의 원인을 다시 봤다. 카탈로그만
주면 LLM이 쓸 수 있는 게 **지표 목록**뿐이라, 문장이 지표를 하나씩 읊는다.
LLM에게 "논지를 세워라"라고 시키는 건 답이 아니다 — 논지를 세우려면 수치를
비교해야 하고, 우리는 의도적으로 수치를 안 보여준다.

그래서 **논지를 결정적으로 계산해 프롬프트에 넣는다**(`build_observations`).

- 마진 브리지: Δ영업이익률 = (−Δ원가율) + (−Δ판관비율). 근사가 아니라 **항등식**이다.
  삼성전자 FY2025 실측 잔차 0.000pp. 어느 비용이 마진을 움직였는지 확정된다.
- 외형 vs 이익 증가율 비교 → 운영 레버리지 작동 여부
- 영업이익과 순이익의 방향 불일치 → 영업외·법인세 요인 분리

**관찰문에는 크기를 쓰지 않는다.** 프롬프트에 들어간 숫자는 LLM이 리터럴로
베낀다. 방향과 우열(어느 쪽이 더 컸는가)만 담고 크기는 플레이스홀더로 본문에
들어간다. 이걸 회귀 테스트로 고정했다.

검산이 안 맞으면 지배 요인을 **말하지 않는다**. 영업이익 정의가 매출−원가−판관비와
다르다는 뜻이므로 단정하지 않고 그 사실을 서술한다.

결과: 투자포인트가 "매출은 X 변동했다"에서 "매출은 10.9% 증가했지만 영업이익은
33.2% 증가해 운영 레버리지가 작동했다"로 바뀌었다. 통과율 100% 유지.

### D17 — 검산값은 감사용이다 (`NumberEntry.internal`)

브리지 잔차를 카탈로그에 넣었더니 LLM이 본문에 "검산 차이는 +0.0pp로 확인된다"를
썼다. 맞는 말이지만 **독자용 문장이 아니다** — 내부 QA 값이다.

`internal=True` 항목은 카탈로그에서 빠지되 레지스트리에는 남는다. 치환·바인딩·
감사 추적은 그대로 되고 LLM만 못 본다. EPS 교차검증 괴리도 같은 처리.

<a id="d18"></a>
### D18 — 정기보고서 주요정보 API 계열을 쓴다

`~/Desktop/samil-hackathon`(사업보고서 3,293건 처리)을 보고 알았다.
`fnlttSinglAcntAll`(재무제표)과 **별개의 API 계열**이 있고, 12개 엔드포인트를
실제 키로 확인한 결과 전부 응답한다. 그중 4개를 붙였다.

| API | 얻는 것 | 왜 필요한가 |
|---|---|---|
| `stockTotqySttus` | 발행·자기·유통 주식수 | **밸류에이션의 분모.** 이게 없으면 시작조차 안 된다 |
| `alotMatter` | DPS·배당수익률·배당성향 | 배당 + **가격 앵커**(아래) |
| `accnutAdtorNmNdAdtOpinion` | 감사의견 + 핵심감사사항(KAM) | 리스크 섹션의 **외부 검증된** 근거 |
| `empSttus` | 부문별 인력 | 사업 구성 단서 |

**KAM이 특히 중요하다.** 감사인이 "여기가 위험하다"고 지목한 항목이라 우리
추측이 아니다. 컴플라이언스 부담 없이 리스크 서술의 근거로 쓸 수 있다. 다만
적정의견 하에서도 KAM은 항상 지정되므로 **부실 신호로 단정하지 않는다.**

실측이 잡아낸 함정 (전부 회귀 테스트로 고정)

- `isu_stock_totqy`는 **수권**주식수다. 쓰면 삼성전자 주식수가 3배가 된다.
  발행주식총수는 `istc_totqy`.
- `성별합계` 행이 DX·DS와 **함께** 온다. 부문으로 세면 총원이 정확히 2배.
- 자기주식 `-`는 미공시가 아니라 0이다. 발행 == 유통 항등식이 확정한다.
- KAM 구분자가 개행 없이 붙는다("…평가2. 재화의…"). 숫자·한글 순서를 둘 다
  쓰고 **순서대로 이어지는 마커만** 인정한다("제3자 배정"의 3을 오인하지 않게).
- `fo_bbm`이 사업부문이 아닐 수 있다. 셀트리온제약은 생산직·영업직 **직군**이다.
  이걸 사업부문으로 서술하면 리포트에 거짓이 들어간다 → `grouping`으로 분류.

**세그먼트에 대해**: DART에 부문별 **매출** API는 없음이 확정됐다. 부문별 인력은
얻었지만 인력 비중은 매출 비중이 아니다. 매출 세그먼트는 사업보고서 원문
파싱이 필요하고, 이는 [D13](#d13)의 우선순위 재검토 대상이다.

<a id="d19"></a>
### D19 — 시세 API 없이 밸류에이션을 시작한다 (역산 주가 앵커)

`KRX_API_KEY`가 없어 [D13](#d13)의 시세 연결이 막혀 있었다. 그런데 밸류에이션에
정말 필요한 건 주식수이고([D18](#d18)), 가격도 부분적으로 얻을 수 있다.

`alotMatter`가 **현금배당수익률**을 준다. DPS ÷ 배당수익률 = 주가다.

가격 없이 확정: BPS · ROE · ROA · 부채비율 · 배당수익률 · 배당성향
역산 앵커로: 주가 · 시가총액 · PER · PBR

**역산 주가는 특정일 종가가 아니다.** DART가 어느 시점 주가로 수익률을 계산했는지
명시하지 않는다(통상 배당기준일 전 일정 기간 종가 평균). 그래서 `is_implied`로
표시하고 라벨에 "역산"을 붙이고 리스크 섹션에 한계를 명시한다. 조용히 쓰면
독자가 종가로 오인한다. 시세 어댑터가 붙으면 대체한다.

**EPS 교차검증**: 재무제표 희석EPS vs 배당공시 (연결)주당순이익. 두 값은 **다른
경로**로 오므로 일치하면 주식수·순이익 기준이 양쪽 다 맞다는 뜻이다. 삼성전자
실측 괴리 −0.03%. 이게 주당 지표가 조용히 틀리는 걸 잡는 유일한 독립 검산이다.

기준을 섞지 않는 것이 핵심이다 — ROE·BPS는 **지배주주**, 부채비율은 **전체**,
시가총액 분모는 **발행**(유통 아님). 실제로 ROE 평균자본에서 당기는 지배주주,
전기는 전체를 쓰는 버그가 있었고 테스트가 잡았다.

### D20 — 커버리지가 다르면 낮은 쪽으로 폴백한다 (주요계정)

파마리서치(214450) FY2025는 사업보고서를 냈고 주요정보 API도 응답하는데
**전체계정(`fnlttSinglAcntAll`)만 013**이다. 두 API의 커버리지가 다르다.

`fnlttSinglAcnt`(주요계정)로 폴백한다. 계정이 30개뿐이라 매출원가·판관비가 없어
[D16](#d16)의 마진 브리지를 못 만들지만, 매출·영업이익·순이익·자산·부채·자본은
있다. **"발간 불가"와 "일부 지표 없음" 사이에서 후자를 택한다** — 코스닥 미커버
소형주가 타깃이므로 전자를 택하면 시장을 잃는다.

이 종목은 이전엔 아예 생성 실패였다. 지금은 지표 7개로 노트가 나오고, 못 찾은
계정은 한글 라벨로 본문에 밝힌다([D5](#d5) 원칙 유지).

주요계정은 형태도 다르다: `fs_div`를 줘도 CFS·OFS를 모두 돌려주고(안 거르면
자산총계가 두 개), `account_id`가 없고, 같은 계정이 중복으로 온다.

<a id="d21"></a>
### D21 — 같은 논지를 두 번 싣지 않는다 (리스크 병합)

[D16](#d16)으로 KAM을 논지로 주면 LLM이 그걸 리스크로 쓴다. 거기에 결정론
문장까지 붙이면 독자가 같은 말을 두 번 읽는다(실측으로 확인).

결정론 리스크에 주제 키워드를 달고, LLM 서술에 그 키워드가 이미 있으면 뺀다
(`merge_risks`). 결정론 쪽은 **누락 방지 안전망**이지 필수 문장이 아니다.

다만 범위 고지 두 줄(공시 밖 요인 미반영 / 추정 미구현)은 LLM이 뭘 쓰든 남긴다.

<a id="d22"></a>
### D22 — 장르는 실적 리뷰 노트다 (톤 결정)

사용자 지적: 출력이 "DART 사업보고서를 회계 펌이 쓴 것처럼" 읽힌다. 맞았고,
원인의 대부분이 이 저장소가 만든 것이었다.

원인 세 가지

1. **KAM을 본문에 인용했다** ([D18](#d18)의 오류). 실제 RA 리포트는
   핵심감사사항을 인용하지 않는다. "감사인이 ~을 지목했다"가 들어가는 순간
   회계법인 산출물처럼 읽힌다.
2. **"추가 확인이 필요하다" 어법.** 공시 밖 요인을 단정하지 말라는 프롬프트가
   실사 보고서 어투를 만들었다.
3. **방법론 고지가 리스크 섹션에 있었다.** "공시 기반 지표만 사용했다"는
   회사의 리스크가 아니라 우리 자료의 한계다.

수정

* KAM 취급을 가른다 — **비적정 의견·강조사항은 본문**(실제로 material),
  **적정의견 하의 KAM은 논지로만.** LLM이 사업 언어로 옮긴다
  ("수익인식 기간귀속" → "매출 인식 시점").
* 프롬프트 맨 앞에 장르 규정을 두고 두괄식을 요구. "추가 확인이 필요하다"를
  금지하고 "관건은 ~다", "~에서 갈린다"로 대체.
* '작성 기준' 섹션 신설 — 방법론 한계를 리스크에서 분리.

**구조적 원인과 그 해법**: 증권사 리포트의 목소리는 뷰에서 나온다.
[D4](#d4)로 목표주가·투자의견을 금지했으니 뷰가 빠진 자리에 "관측의 나열"만
남고, 그건 필연적으로 회계 문서가 된다.

목표주가는 계속 내지 않는다. 대신 **논지**를 낸다 — 규제 대상이 아니다.
'관전 포인트' 섹션을 추가했다: "무엇이 확인되면 판단이 달라지는가". 검증
가능해야 하고 "지속적인 모니터링이 필요하다" 같은 문장은 금지다.

사용자 문서(`what-makes-a-great-research-report.md` §2)가 말하는
*"the text ... **is** the informational content"*가 빠져 있었던 것이다.

<a id="d23"></a>
### D23 — 조사(助詞)는 치환 시점에 교정한다

LLM은 `{{num:...}}으로`라고 쓰지만 **치환될 값의 끝소리를 모른다.** 값을
안 보여주는 게 이 시스템의 전제([D15](#d15))라 알 수도 없다. 실측:

    40.0%으로 → 40.0%로     70.1%이 → 70.1%가
    53.2%을  → 53.2%를     44.2%과 → 44.2%와

단위가 조사를 결정하고 단위는 치환 시점에 확정되므로 **판단이 아니라
계산**이다. `render_text`가 치환하면서 고친다.

서술격조사는 건드리지 않는다 — "25.9%이며"는 받침이 없어도 원형이 표준이라
"25.9%며"로 고치면 오히려 나빠진다. 주격조사 `이`만 고친다.

<a id="d24"></a>
### D24 — 추정치는 가정의 함수다 (추정 레이어)

`what-makes-a-great-research-report.md` §1: FnGuide 배점의 **40점이 실적 추정
정확도**다. §4: 하향 조정이 상향보다 72일 늦는 것이 신뢰가 무너지는 지점이다.
추정은 리포트의 부속물이 아니라 평가 대상 그 자체이고, **초기 추정보다 수정
이력이 더 중요하다.**

지금까지의 원칙("확인된 것만 쓴다")과 충돌하지 않는다. 추정 레이어는 그
원칙의 **명시적 적용**이다:

* 모든 추정치는 가정에서 계산된다. 가정이 없으면 값도 없다.
* 가정은 전부 표시된다 — 값과 **근거**(`basis`)까지.
* 기본 가정은 과거 실적의 기계적 연장이고, 이건 예측이 아니라 **기준선**이다.
  그렇게 라벨링한다.
* 사람이 덮어쓰면 `is_override`로 구분되고 산출 방식이 "사용자 지정"으로 바뀐다.

**가정도 수치다.** 처음엔 가정을 문장에 리터럴로 썼고 G0가 바로 막았다.
가정 역시 레지스트리에 등록하고 플레이스홀더로 쓴다.

기계적 연장의 한계를 두 겹으로 막는다 — 성장률이 −50~100% 밖이면 산출하지
않고, 최근 성장률의 진폭이 20pp를 넘으면 경고를 단다. 사람이 명시적으로
지정하면 두 제한 모두 우회한다(판단의 주체가 다르다).

<a id="d25"></a>
### D25 — revision 이력은 발간일로 찍는다

추정 스냅샷의 시각을 실행 시각(wall clock)으로 찍으면 "그 시점에 무엇을
추정했는가"라는 point-in-time 질문에 답할 수 없고, 발간일 기준 as-of 조회가
어긋난다(실측으로 확인 — revision이 0건으로 나왔다).

`save_snapshot(snapshot_at=발간일)`로 찍고, 조회는 **이번 발간일 직전**으로
자른다(오늘 저장한 값을 다시 읽어 "변화 없음"이 되는 걸 막는다).

**게이트를 통과한 초안의 추정만 저장한다.** 차단된 초안의 추정이 다음 발간의
비교 기준이 되면 이력이 오염된다.

이것이 [D12](#d12)의 정합성 표시 3종이 서 있을 토대다. 실측 확인:
1차 발간 추정 7,704억원 → 가정 하향 후 2차 6,435억원, **하향 −16.5%**로
표에 잡힌다.

<a id="d26"></a>
### D26 — 화면은 서버 렌더로 먼저 세운다 (표면 v0) — [D37로 이관됨](#d37)

장기 계획은 Next.js + FastAPI다(ARCHITECTURE.md). 다만 이 화면의 목적은
**검토 흐름을 눈으로 확인하는 것**이지 프론트엔드 아키텍처 검증이 아니다.
서버 렌더(FastAPI + Jinja2)로 먼저 세우고, 같은 프로세스에 `/api/reports`를
열어 둔다 — Next.js가 나중에 그대로 호출하므로 버리는 코드가 아니다.

화면이 증명해야 하는 것은 셋이고, 셋 다 엔진이 이미 갖고 있는 성질이다:

1. **숫자를 클릭하면 출처가 나온다.** Number Registry가 없으면 불가능하고,
   이게 ChatGPT 대비 유일한 구조적 차별점이다.
2. **게이트가 보인다.** 통과/차단과 위반 내역이 화면에 있어야 "사람이 검토
   후 발간"이 성립한다. **차단된 초안은 본문을 렌더하지 않는다** — 보여주면
   검토자가 결과로 착각한다.
3. **가정을 바꾸면 추정이 바뀐다.** [D24](#d24)를 조작으로 보여준다.

이를 위해 `render/html.py`를 별도로 뒀다. CLI의 `render_text()`는 평문이라
출처가 사라진다. HTML 경로는 값을 `<span data-key data-formula data-doc …>`로
감싸되 **같은 레지스트리·같은 조사 교정**([D23](#d23))을 쓴다 — 화면과 파일의
숫자가 갈라질 수 없다.

부수 발견: `dart_reports.py`가 `Provenance`에 없는 `document_id=`를 넘기고
있었고 pydantic이 조용히 버렸다. 화면에 출처를 붙이려다 드러났다 —
**표면을 만들면 데이터 레이어의 구멍이 보인다.**

<a id="d27"></a>
### D27 — 생성과 발간은 다르다 ([D25](#d25) 수정)

D25는 추정 이력 조회 경계를 "발간일 **직전**"으로 잡았다. 자기 자신과
비교하는 걸 막기 위해서였는데, 그 전제가 "생성할 때마다 저장한다"였다.

화면을 만들면서 그 전제가 틀렸음이 드러났다. 생성할 때마다 저장하면 **가정을
만지작거린 흔적이 전부 "직전 추정"이 되어 이력이 무의미해진다.** 그리고 같은
날 발간 후 가정을 고쳐 다시 생성하면 변화가 보이지 않는다(실측).

바로잡은 모델:

* **생성** = 미리보기. 이력에 남지 않는다.
* **발간** = 검토 완료 선언. 이때만 추정을 스냅샷으로 저장하고 노트를 파일로
  쓴다. [D25](#d25)의 "게이트 통과분만 저장" 원칙은 그대로다.

저장이 발간에서만 일어나므로 조회 경계를 **발간일 끝(포함)**으로 되돌릴 수
있다. `build_report`는 저장보다 먼저 끝나므로 자기 비교 위험이 없다.

이건 기술 결정이 아니라 제품 결정이다 — "사람이 검토 후 발간"이라는 전제가
화면에서 두 개의 버튼으로 나타난 것이다.

<a id="d28"></a>
### D28 — 부문별 매출은 원문에서 뽑되, **매출액으로 검산해서만** 쓴다

[D18](#d18)에서 DART에 부문별 매출 API가 없음이 확정됐다. 남은 경로는
사업보고서 원문 「II. 사업의 내용 → 4. 매출 및 수주상황」의 표뿐이다.
`/api/document.xml`은 ZIP을 주고, 그 안 5~8MB XML에 DART 고유 표 태그가 있다.

원문 파싱은 API보다 훨씬 깨지기 쉽다. 회사마다 표가 다르다(실측):

| 회사 | 라벨 열 구조 |
|---|---|
| 파마리서치 | 구분 \| 판매구분 \| 금액 \| 비율 |
| 삼성전자 | 품목 \| 금액 |
| SK하이닉스 | 사업부문 \| 매출유형 \| 품목 \| 금액 |
| 셀트리온제약 | 사업부문 \| 매출유형 \| 품목 \| 판매구분 \| 금액 |

그래서 **파싱 결과를 믿지 않는다.** 부문 매출의 합은 손익계산서 매출액과
같아야 하고, 이 항등식이 파서를 외부에서 검증한다:

    Σ(부문 매출) ≈ 매출액   그리고   Σ(비중) ≈ 100%

[D16](#d16)의 마진 브리지와 같은 원리다. **검산이 닫히지 않으면 표시하지
않는다** — 잘못 읽은 부문 구성이 리포트에 실리면 되돌릴 수 없다.

구조는 고정 위치를 가정하지 않고 데이터에서 추론한다. 라벨 열 개수는 다수
행이 동의하는 위치로, 판매구분 열은 **내수·수출이 실제로 있는** 열로 정한다
(소계만 보고 고르면 전체 합계 행 하나 때문에 부문명 열이 잡힌다).

가장 어려웠던 것은 **중첩 소계**다. 셀트리온제약은 품목별 합계와 유형별
소계가 한 표에 함께 실려 있어 다 더하면 매출액의 1.77배가 된다. 계층 레벨별
후보를 만들어(레벨 L보다 깊은 라벨이 전부 비었거나 소계인 행만) 검산이
통과하는 것을 고른다. `제품소계` 같은 표기 때문에 소계 판정은 부분 일치다.

실측 4종목 전부 ±0.00%로 닫혔다. 부문이 하나여도 쓴다 — "반도체 단일"은
그 자체로 리포트에 실릴 사실이다.

**남은 한계**: 이 표는 제품·품목 기준이라 회계기준서상 영업부문(주석)과
다를 수 있다. 부문별 **이익**은 여전히 없다.

### D29 — 리포트가 손익계산서에서 출발하지 않는다 (사업 이해 레이어)

벤치마크(SMIC 15건, 29~36쪽)와 우리 노트(2쪽)의 갭을 좁히려다 원인에 닿았다.
분량은 결과이고 원인은 **회사가 무엇을 하는 회사인지 몰랐다는 것**이다.
[research/01](research/01-benchmark-smic.md) §3이 "리포트는 손익계산서에서
출발하지 않는다"고 진단했는데, 우리는 계속 거기서 출발하고 있었다.

재료는 이미 공시에 있었다. 「II. 사업의 내용 → 1. 사업의 개요」에 회사가 직접
쓴 사업 서술이 6,714자 있는데 한 글자도 안 읽고 있었다.

새로 읽는 것

| 소스 | 얻는 것 |
|---|---|
| 「1. 사업의 개요」 | 제품·핵심기술·자회사·해외전략 |
| 「2. 주요 제품 및 서비스」 | **3개년** 부문별 매출 (「4. 매출 및 수주상황」보다 표가 단순하고 연도가 나란히 있다) |
| `hyslrSttus` | 최대주주·특수관계인 지분율 |
| `otrCprInvstmntSttus` | 경영참여 출자처 |

**숫자 불변식은 그대로다.** 원문에는 등록되지 않은 숫자가 가득해서 그대로
넣으면 LLM이 리터럴로 베낀다. `mask_numbers()`로 가리되 **탐지와 같은
화이트리스트**를 쓴다 — 두 규칙이 갈라지면 "가렸는데 게이트에 걸리는" 상황이
생긴다. 연도는 남긴다(사실이고 게이트도 허용한다).

즉 LLM이 받는 것은 **질적 사실**(무엇을 파는가·어떤 기술인가·어디에 파는가)
이고 크기는 여전히 레지스트리만 안다.

게이트가 두 번 잡았다: 자회사 지분율을 표에 리터럴로 넣었다가 차단됐고(→
레지스트리 경유), 계층 제목 `### 2.1`의 2.1이 소수로 잡혔다(→ 화이트리스트에
계층 번호 추가. 본문의 2.1은 여전히 막힌다).

**지주형 판정은 건수가 아니라 비중으로.** 경영참여 12건이라고 지주사가 아니다.
파마리서치는 출자 장부가가 자산의 10.3%뿐인 사업회사이고 소액 투자조합이
건수를 부풀린다. 자산의 절반 이상이 묶여야 밸류에이션 방법이 달라진다.

<a id="d30"></a>
### D30 — 투자포인트는 논증이다 (반론이 없으면 소개다)

벤치마크의 투자포인트는 제목이 주장이고 5쪽에 걸쳐 논증한다. 우리는 3~5문장
관찰이었다. 프롬프트에 네 요소를 순서로 강제했다:

**주장**(두괄식) → **근거**(수치) → **반론**("다만 ~라면 이 해석은 성립하지
않는다") → **확인 지점**(다음 공시에서 볼 것)

반론이 핵심이다. 반론 없는 투자포인트는 주장이 아니라 소개다. 그리고 반론을
쓰려면 자기 논지가 어디서 깨지는지 알아야 해서, 논지 자체가 단단해진다.

제목도 라벨이 아니라 주장이어야 한다 — "수익성 개선"(무엇을 주장하는지 없음)이
아니라 "이익률 개선은 원가에서 왔고, 재현 가능성이 관건이다".

<a id="d31"></a>
### D31 — 미검증 레인을 허용하는 조건은 "숫자가 없을 것"

벤치마크의 1~2장은 매크로·정책·산업 서사인데 공시에 없다. 사용자 결정으로
**별도 미검증 레인**을 열되 표시한다: 「0. 산업 배경」 + ⚠ 배지 + 작성 기준 명시.

이 레인을 허용할 수 있는 이유는 하나다 — **숫자가 없기 때문이다.**

* 수치 카탈로그를 주지 않는다.
* **두 번째 LLM 호출로 분리한다.** 같은 호출에 섞으면 재무 서술로 변질된다.
* 숫자가 하나라도 있으면 **문단만 버린다.** 리포트 전체를 막지 않는 이유는,
  검증 불가능한 레인 하나 때문에 검증된 나머지를 못 내보내는 게 합리적이지
  않아서다.

**다른 섹션보다 엄격하다.** G0 화이트리스트는 연도를 허용하지만 이 레인에서는
연도도 막는다 — "2025년부터 규제가 바뀌었다"는 아무도 확인할 수 없다.
테스트가 이걸 잡아서 알았다.

부수: LLM이 부문 매출 비중을 말하며 "비중 확대"를 썼는데 이건 투자의견
(overweight)이라 문맥과 무관하게 차단된다. [D22](#d22)와 같은 처방 — 본문에서
rating 어휘를 아예 안 쓰게 했다.

<a id="d32"></a>
### D32 — 차트는 수치의 두 번째 출처가 되면 안 된다

SVG `<text>`는 G0 스캔 대상이 아니다. 차트에 값 라벨을 넣으면 **게이트 밖에서
수치가 생긴다.** 그래서 형태로 비교만 보여주고 정확한 값은 바로 위 표에 둔다.
차트가 두 번째 출처가 되면 표와 갈라질 수 있고, 갈라져도 아무도 못 잡는다.

외부 차트 라이브러리를 쓰지 않는 이유: 웹은 인라인 정책을 전제로 만들었고
마크다운 산출물은 파일 하나로 완결돼야 한다. 순수 SVG 문자열이면 양쪽 다 된다.

<a id="d33"></a>
### D33 — 부문별 이익은 주석에서 뽑고, **총계 열로** 검산한다

[D28](#d28)로 부문별 **매출**은 얻었지만 정작 애널리스트가 묻는 질문에는
답하지 못했다: **어느 부문이 돈을 버는가.** 기업회계기준서 제1108호가
보고부문별 손익을 주석으로 요구하고, `<TE>` 셀 파싱이 열리면서 거기 닿았다.

표가 매출 표와 **전치**돼 있다 — 행이 계정, 열이 부문이다. 그래서 D28의
파서를 쓸 수 없다. 제목도 갈린다: 「부문별 보고」·「부문별정보」·「영업부문」·
「영업부문 정보」·「부문정보」.

**검산 방식이 D28과 다르다.** D28은 Σ(부문) = 매출액을 요구했는데, 부문
주석에서는 이걸 요구하면 **정상 공시를 거부한다**:

| 회사 | Σ(부문 매출) ÷ 연결 매출액 |
|---|---|
| LG전자 | 1.00 |
| 롯데케미칼 | 1.08 |
| 삼성전자 | 1.09 |
| CJ제일제당 | 1.35 |

부문 매출에는 내부거래가 남아 있고 별도 표시하지 않는 「기타」가 있다.
대신 주석 자신이 주는 **기업 전체 총계 열**을 쓴다:

    총계 열의 매출액   ≈ 손익계산서 매출액
    총계 열의 영업이익 ≈ 손익계산서 영업이익      ← 둘 다, **같은 열**에서

두 값은 완전히 다른 경로로 온다(원문 표 파싱 vs `fnlttSinglAcntAll` API).
서로 무관한 두 값이 같은 열에서 동시에 맞을 확률은 무시할 수 있으므로, 이
하나가 행·열·단위를 전부 검증한다. 실측: 삼성전자·LG전자·CJ제일제당은
**자릿수까지 일치**, 롯데케미칼은 18.5조에 78원(반올림) 차.

부수적으로 얻은 것: 단위를 캡션에서 못 읽어도 된다. 검산이 통과하는 배율을
고르면 되고, 그게 캡션보다 강한 근거다.

**섹션도 검산이 고른다.** 같은 보고서에 연결과 별도 주석이 함께 실린다.
제목으로는 가릴 수 없으니 후보를 전부 넘기고 총계가 맞는 것을 쓴다 —
연결 분석에 별도 주석이 섞이는 경로가 여기서 막힌다.

실측 결과

| 회사 | 결과 |
|---|---|
| 삼성전자 | DX·DS·SDC·Harman. **매출 1위 DX(6.8%), 이익 1위 DS(19.1%)** |
| LG전자 | 6개 부문, MS가 영업적자 |
| 롯데케미칼 | 4개 부문, 2개 적자, 단위 천원 |
| CJ제일제당 | 식품·바이오·물류 |
| SK하이닉스·파마리서치·셀트리온제약 | 단일 부문 — 주석 없음. **정확히 거부됨** |

리포트가 답할 수 있게 된 것

* 매출 1위와 이익 1위가 **다르면** 그것 자체가 투자포인트다. 전사 지표에는
  이 사실이 아예 나타나지 않는다.
* 부문별 이익률의 **방향이 갈리면** 전사 마진 변화를 전사 공통 요인으로
  설명할 수 없다.

**전사를 끌고 간 부문은 이익률 변동 폭이 아니라 이익 변화액으로 가른다.**
LG전자 기타부문은 이익률이 10.8pp 흔들렸지만 매출 비중이 2.4%라 전사에는
거의 영향이 없다. 실제 주범은 MS(-1.0조)다. [D28](#d28)의 기여도 판정과
같은 이유이고, 처음엔 여기서 틀렸다.

**적자가 섞이면 이익 비중을 내지 않는다.** 분모가 작아지거나 부호가 뒤집혀
"이 부문이 이익의 105%"가 나온다. 매출 비중만 낸다.

부수 결함(게이트가 잡음): 롯데케미칼 출자 현황의 법인명에 각주 표시가 붙어
온다(`LOTTE Chemical Titan Holding Berhad (*6)`). 본문 표에 그대로 실려 G0가
발간을 막았고, **그건 옳은 판정이다** — 레지스트리에 없고 뜻을 보장할 수 없는
숫자다. 게이트를 푸는 대신 이름에서 각주를 뗐다.

**남은 한계**: 부문별 자산·설비투자는 아직 읽지 않는다. 부문 ROIC을 내려면
필요하다.

### D34 — 기준선의 성적을 재고 공개한다 (백테스트)

[D12](#d12)는 추정 정확도를 최우선 차별화로 올렸고 [D24](#d24)는 추정 레이어를
지었는데, 정작 **우리 기준선의 성적은 몰랐다.** 선언과 실측 사이의 빈칸이다.
`finmodel/backtest.py` · `arc backtest`.

**시점 정합성이 전부다.** FY(Y+1)의 정보가 한 톨이라도 섞이면 백테스트는 좋은
숫자를 내면서 거짓말을 한다. 두 방향을 코드가 막는다: 추정은 FY(Y) 보고서만으로
만들고(그 안에 FY(Y-1)·FY(Y-2)가 비교표시로 있다), 실적은 FY(Y+1) 보고서의
**당기** 값을 쓴다(뒤 보고서의 비교표시는 재작성이 반영돼 다른 질문에 답한다).

측정 결과 — 활동 중인 코스닥 100곳 × FY2021~2024 (n=337)

| | 오차 중앙값 | 편향 중앙값 | ±20% 내 | 매출 대비 | 흑/적 방향 | 폭발(>100%) |
|---|---|---|---|---|---|---|
| 매출액 | **18.5%** | +6.5% | 53% | — | 100% | 5% |
| 영업이익 | 55.9% | +6.8% | 23% | **4.7%p** | 81% | 33% |
| 당기순이익 | 66.4% | +10.8% | 19% | 5.6%p | 81% | 36% |

커버리지: 400쌍 중 363쌍(91%)이 대조 가능, 그중 337건(93%)에서 추정을 냈다.

**읽는 법**: 매출 기준선은 참고용으로 쓸 만하다(절반이 ±20% 안). **이익
기준선은 그렇지 않다** — 매출의 4.7%p를 빗맞히고, 5곳 중 1곳은 흑자·적자
방향조차 틀린다. [D24](#d24)가 "예측이 아니라 출발점"이라 라벨링한 것이
과한 겸손이 아니었다.

측정이 바로잡은 것 셋

1. **평균을 대표값으로 쓰면 안 된다.** 첫 집계에서 매출 편향이 +118%로 나왔는데
   +20,852% 한 건이 만든 값이었고 중앙값은 +6.6%였다. 같은 표본에서 "두 배 넘게
   과대추정한다"와 "7% 위로 기운다"가 갈린다. 중앙값을 앞세우고 평균은 보관만 한다.
2. **이익 오차는 매출로 나눠 읽어야 한다.** 영업이익 5,700만원인 회사에 −63억을
   추정하면 −11,204%다. 크다는 것 말고 읽을 게 없다. [D33](#d33)에서 부문 손익을
   검산할 때 쓴 척도와 같은 이유다.
3. **표본이 답을 만들었다.** corpCode 인덱스에는 **상장폐지된 회사가 남아 있다**
   (stock_code가 유지된다). 무작위로 뽑으니 절반이 텔슨정보통신·코오롱유화 같은
   폐지 종목이었고 "데이터 커버리지 47%"가 나왔다. 직전 사업연도 재무제표가
   나오는 곳으로 좁히니 **91%**다. 앞의 숫자는 우리 파이프라인의 성질이 아니라
   표본의 성질이었다.

**산출 거부는 오차가 아니다.** 성장률이 −50~100% 밖이면 추정을 내지 않는데
([D24](#d24)) 이걸 오차 0으로 세면 성적이 좋아 보이고, 무한대로 세면 나빠 보인다.
따로 세고 커버리지로 보고한다.

**한계**: 직전 사업연도 공시로 표본을 좁혔으므로 기간 중 사라진 회사가 빠진
**생존 편향**이 있다. 숨기지 않는다.

이 숫자를 리포트에 싣는 것은 다음 단계다 — [D12](#d12)의 정합성 표시 3종이
설 자리이고, "우리 기준선의 과거 오차는 이만큼"이라고 밝히는 것이 그 자체로
차별화다.

<a id="d33-2"></a>
### D33 보강 — 부문 감가상각·자산 (Q12 해소)

[D33](#d33)이 연 표에 감가상각비가 함께 있었다. **같은 격자의 다른 행이라 열
배치와 단위는 이미 검증돼 있다** — 비싼 검증은 표·열·단위 식별이고 그건
매출·영업이익 총계가 끝냈다. 그래서 추가 검산 없이 읽는다.

얻은 것: **부문 EBITDA 마진.** 실측 4사 전부 나온다.

| 삼성전자 | 영업이익률 | EBITDA 마진 | 상각 부담 |
|---|---|---|---|
| DX 부문 | 6.8% | 9.2% | 2.4pp |
| **DS 부문** | 19.1% | **48.9%** | **29.8pp** |

영업이익률만 보면 DS가 DX보다 세 배 남는 사업이지만, 상각 전으로는 다섯 배다.
**두 사업은 같은 종류의 수익성이 아니다.** 전사 지표는 물론 부문 영업이익률만
봐도 이 차이가 보이지 않는다.

부문 **자산**은 다른 표라 따로 검산한다(재무상태표 자산총계와 대조). 다만
검산 근거가 하나뿐이라(손익은 매출·영업이익 둘) 구조 조건으로 보강했다 —
**총계 열은 부문 열보다 뒤에 있어야 한다.** 이 조건이 없으면 자산총계와 우연히
가까운 부문 열 하나가 총계로 위장하고 그 왼쪽 몇 개만 부문으로 잡힌다(테스트가
잡았다).

공시 여부가 갈린다: LG전자·롯데케미칼은 있고, 삼성전자는 「보고부문별 자산과
부채는 경영위원회에 정기적으로 제공되지 않아 포함하지 않았습니다」라고 명시한다.
기준서가 CODM에게 정기 제공될 때만 요구하므로 **없는 게 결함이 아니다.**

두 가지를 실측이 바로잡았다:

* **부문명이 조정 열에서 되풀이돼** 빈 값이 부문 자산을 덮어썼다(롯데케미칼).
  합계 열에서 끊는다 — [D33](#d33)의 손익 파서와 같은 처방이다.
* **자산 표가 부문을 약칭으로 부른다**(LG전자: HS·MS·VS). 위치로 짜맞추지 않고
  손익 표의 「각 보고부문의 약칭」 행이 준 대응표를 쓴다. 짝이 없는 부문
  (「기타부문」 vs 「기타부문 및 내부거래」)은 그것만 비운다 — 전부 버리면
  나머지 다섯의 자산까지 잃는다.

잔여 버킷은 논지의 주어가 되지 않는다. LG전자 「기타부문」은 매출 비중 2.4%인데
상각 부담이 가장 무거워 1위로 잡혔다. 매출 비중 5% 미만은 이 문장에서 뺀다
([D33](#d33)의 기여도 판정과 같은 이유이고, **세 번째로 같은 함정을 밟았다**).

### D35 — View는 **인물이 아니라 렌즈**로 낸다

[D22](#d22)가 진단한 빈 곳이 남아 있었다 — 목표주가·투자의견을 금지했으니
뷰가 빠진 자리에 관측의 나열만 남는다. 「관전 포인트」를 만들었지만 얇았다.

제안된 안은 **실명 페르소나**였다: 버핏 주주서한을 읽혀 에이전트로 만들고,
애크먼도 그렇게 만들어 3~4개 관점의 variation을 준다. 계기는 홍콩 서비스
Edgen이었는데, 조사해 보니 **Edgen의 17개 에이전트는 기능별이지 페르소나가
아니다.** 그 패턴의 실제 출처는 `virattt/ai-hedge-fund`(GitHub 51.7k)이고,
스스로 proof-of-concept이라 밝힌 데모다 ([research/05](research/05-view-and-personas.md)).

**실명 페르소나는 채택하지 않는다.** 둘이 치명적이다:

* **D4와 정면 충돌** — "버핏이라면 샀을 것"은 우회가 아니라 투자의견 그 자체다.
* **실존 인물 사칭** — 살아 있는 실명 인물에게 하지 않은 말을 귀속시킨다.
  "조사분석자료가 아님" 면책은 명예훼손·퍼블리시티권과 무관하다.

덧붙여, 크기를 못 보는([불변식 1](#d15)) 페르소나는 말투만 남고, 정확도를 잴
수 없어 [D34](#d34)로 세운 "측정 가능성이 해자"와 모순된다.

**대신 렌즈를 쓴다.**

> 페르소나는 **결론**을 내지만, 렌즈는 **다른 질문**을 던진다.
> 같은 검증된 숫자에 서로 다른 질문을 던지고, **답이 갈리는 지점이 곧 View다.**

| 렌즈 | 질문 | 재료 |
|---|---|---|
| **자본수익률** | 투입 자본 대비 얼마를 버는가 | 부문 자산·ROA·EBITDA([D33 보강](#d33-2)) · ROE · 출자 장부가 |
| **재현성** | 이번 이익은 반복되는가 | 마진 브리지([D16](#d16)) · 부문별 이익률 방향 · 영업이익 vs 순이익 |

렌즈는 결정적 코드가 관찰문을 만들고 LLM은 글로만 옮긴다 — [D16](#d16)과 같은
패턴이라 불변식이 깨지지 않는다. 렌즈가 **질문**이지 **판정**이 아니므로 D4도
건드리지 않고, 렌즈 A의 결론이 렌즈 B의 반론이 되어 [D30](#d30)과 이어진다.

**렌즈가 갈리는 지점을 「관전 포인트」에 싣는다.** D22가 만들고 못 채운 섹션이
여기서 채워진다. 실측: 롯데케미칼은 자산가치로 보면 싸지만 자산 31.1조 중
24.0조가 영업적자 부문에 묶여 있다 — **"싸 보이는 이유가 자산이 안 벌기
때문"**이고, 전사 지표로는 나오지 않는 논지다.

버핏 주주서한은 그래도 읽는다. 다만 **이름을 산출물에 붙이지 않는 용도**다 —
뽑을 것은 그의 결론이 아니라 **어떤 질문을 먼저 던지는가**이고, 그게 렌즈
설계의 입력이 된다. [D11](#d11)이 SMIC에 적용한 원칙과 같다: 구조는 학습하고
논조는 학습하지 않는다.

**실패 조건을 미리 적는다.** 렌즈가 갈리는 회사가 거의 없다면 이 설계는
복잡성만 늘린 것이다. 그때는 접고 관전 포인트를 다른 방식으로 채운다.

<a id="d35-2"></a>
### D35 보강 — 뷰의 차이는 부호가 아니라 **순서와 다음에 볼 것**에서 온다

초판은 렌즈마다 `stance`를 하나 두고 "부정이 하나라도 있으면 부정"으로 접었다.
사용자 지적이 이걸 무너뜨렸다 — *"같은 긍정이라도 말하는 태도의 차이가 클 수
있다. 중요하게 보는 요소가 다르거나, 같더라도 우선순위나 평가하는 보조지표가
다르거나."*

**맞았고, 만든 것에서 바로 증거가 나왔다.** LG전자 자본수익률 렌즈의 주된
발견은 「자산이 흑자 부문에 배치돼 있다」(긍정)인데, 부차적인 레버리지 관찰
하나 때문에 렌즈 전체가 부정으로 접혀 **1순위 발견과 정반대 문장**이 관전
포인트에 실렸다. 만든 것은 렌즈가 아니라 부호 하나로 접히는 스위치였다.

세 축을 코드에 대응시켜 다시 짰다:

| 축 | 대응 |
|---|---|
| 무엇을 보는가 | 렌즈마다 다른 데이터 (초판에도 있었음) |
| **무엇을 먼저 보는가** | `chain` — 질문 사슬이 순서를 고정한다 |
| **다음에 무엇을 볼 것인가** | `watch` — 렌즈마다 다음 분기에 볼 숫자를 하나 지목한다 |

**우선순위는 임의가 아니라 질문에서 도출된다.** 자본수익률 렌즈의 사슬은
「자본이 어디에 놓여 있는가 → 그 자본이 버는가 → 지금 수익률이 무엇에서
오는가」이고, **1단계를 모르면 2단계를 말하지 않는다.** 임의로 매기면 그건
페르소나를 기각한 이유(근거 없는 판단)를 렌즈 이름으로 되풀이하는 것이다.

렌즈는 이제 부호로 접히지 않고 **주된 발견(headline) + 단서(caveat) + 다음에 볼
것(watch) + 답하지 못한 질문(unanswered)**으로 남는다. LG전자는 이제 이렇게 나온다:

> 자산이 대체로 흑자 부문에 배치돼 있다.
> **다만** — 자기자본이익률이 총자산이익률을 크게 웃돈다. 그 차이는 부채 사용에서 온다.

**충돌도 세 종류로 갈렸다:**

| 종류 | 언제 |
|---|---|
| `verdict` | 두 렌즈의 결론이 갈린다 (초판이 유일하게 잡던 것) |
| `grounds` | **결론은 같은데 볼 숫자가 다르다** |
| `caveat` | 한 렌즈 안에서 주된 발견과 뒤 판독의 방향이 갈린다 |

`grounds`가 특히 중요하다. 초판은 둘 다 긍정이면 **아무 말도 안 했는데, 그때가
독자를 가장 오도하기 쉽다** — "합의됐다"로 읽히지만 실제로는 서로 다른 방식으로
맞을 수 있다는 뜻이다.

**「답하지 못한 질문」도 출력한다.** 삼성전자는 부문 자산을 공시하지 않아
1순위 질문에 답하지 못한다. 그 사실 자체가 회사에 대한 정보다. 이걸 숨기면
"확인했는데 문제없다"로 읽힌다.

**부수 확인 — 페르소나 기각이 옳았다는 방증.** 사용자가 같은 저자의 후속
프로젝트 [`virattt/dexter`](https://github.com/virattt/dexter)를 짚어 줬는데,
**페르소나를 버리고 기능형 에이전트 + 작업 분해 + 자기검증으로 갔다.**
페르소나 프로젝트를 바이럴시킨 본인이 다음 것을 그렇게 짓지 않았다. 다만
Dexter는 README에 *"결과가 틀리거나 불완전할 수 있다"*고 명시하며 검증을
포기한다 — 우리는 그 문장을 쓸 수 없고, 그게 차이의 전부다.

Dexter에서 가져올 만한 것은 **작업 분해 자체를 산출물로 보여주는 것**이고,
`chain` + `unanswered`가 그 자리다. 우리 쪽이 더 강한데, 계획이 고정이라
**어느 질문에 답했고 어느 질문에 못 답했는지가 검증 가능**하기 때문이다.

### D35 보강 2 — 렌즈는 **타깃 시장의 데이터에서** 고른다

사용자 지적: *"작업이 안 되었는데 푸시가 무슨 소용이야."* 맞았다.

초판·2차 모두 **대형주 4곳**(삼성전자·LG전자·롯데케미칼·CJ제일제당)으로 검증하고
일반화했다. 타깃인 코스닥 25곳에서 재보니 참사였다:

| | 초판 |
|---|---|
| 자본수익률 렌즈가 요구하는 **부문 자산** | **0/25** |
| 그 렌즈가 낸 "결론" | 전부 3순위 관찰(ROE vs ROA) 하나 |
| 그 문장 | **다섯 곳이 글자까지 동일** |
| 관점 충돌 | **4/25 (16%)** |

[D3 보강](#d3-보강)이 이미 기록한 실패 모드(*"NVDA와 TSLA가 글자까지 동일한
앵글을 받는다"*)를 렌즈 이름으로 재현한 것이다.

**먼저 데이터를 재고 그 위에서 렌즈를 골랐다** (코스닥 22곳 실측):

    최대주주·ROE·사업개요 100% · 부문 매출 82% · 출자 장부가 73% · 다부문 64%
    마진 브리지 55% · 자기주식 50% · 배당성향 27% · 부문 자산 0%

내가 고른 두 렌즈가 하필 가장 희소한 데이터를 요구했다. 세 렌즈로 다시 짜되
**1순위 질문을 가용률 높은 것으로** 놓았다:

| 렌즈 | 1순위 질문 | 가용 |
|---|---|---|
| **자본** | 투입한 자본이 수익을 내는가 (ROE) | 100% |
| **집중** | 매출이 어디에 몰려 있는가 (부문 매출) | 82% |
| **재현성** | 무엇이 마진을 움직였는가 (브리지) | 55% |

**구조 규칙 하나가 상용구를 막는다: 1순위에 답하지 못하면 결론을 내지 못한다.**
뒤 단계 관찰은 맥락으로 남되 판정이 되지 않는다. 이 규칙이 없어서 "다섯 곳 같은
문장"이 나왔다.

**판독은 회사를 지목한다.** 부문명·출자처·최대주주 이름을 부르고, 크기는
`slots`으로 플레이스홀더가 물고 온다. 이름도 숫자도 없는 판독은 상용구다.

결과 (같은 코스닥 22곳)

| | 초판 | 2차 수정 |
|---|---|---|
| 자본 관련 렌즈 결론 | 실질 0% | **100%** |
| 집중 렌즈 결론 | — | 45% |
| 재현성 렌즈 결론 | 55% | 55% |
| **관점 충돌** | **16%** | **73%** |

파마리서치(타깃 시장 대표)가 **두 렌즈 침묵 → 자본·집중 모두 발화**로 바뀌었다.

실측이 두 결함을 더 잡았다:

* **D28 파서가 「제품」·「-」를 부문명으로 뽑는다.** 그대로 인용하니 "매출이
  제품에 몰려 있다"가 나왔다 — 아무 말도 아니다. 이름을 못 믿으면 사업 집중을
  말하지 않는다(집중 렌즈 결론이 82%→45%로 내려간 대가다. 정직한 쪽을 택했다).
* **이름 뒤 조사가 틀린다.** "화장품은 늘고 **기타은** 줄었다". [D23](#d23)의
  치환 시점 교정은 플레이스홀더 뒤만 고치므로, 결정적 코드가 이름을 넣을 때는
  `josa.attach()`로 받침을 보고 골라야 한다.

**교훈은 렌즈보다 크다.** 이 저장소는 4종목 회귀 세트로 검증해 왔는데 그중
셋이 대형주다. **타깃이 코스닥 미커버 소형주라면 검증도 거기서 해야 한다.**

### D36 — 출처는 **항목마다 다르고, 파일에도 남는다**

사용자 지적: *"RA 분들은 출처에 굉장히 민감할 것 같은데, 중간중간 출처를 표기하고
클릭 가능하게 해서 직접 검증할 수 있게 해야 하지 않나."*

[D26](#d26)으로 웹에서 숫자를 클릭하면 팝오버가 뜨긴 했다. 그런데 실측해 보니
**바인딩 47건이 전부 같은 출처 하나**를 가리켰다.

원인: 데이터 레이어에는 API별 provenance가 **이미 있는데** 파이프라인이 전부
`stmt.provenance`(재무제표)로 덮어쓰고 있었다. 배당성향은 `alotMatter`,
최대주주 지분은 `hyslrSttus`, 부문 매출은 **원문 표 파싱**에서 왔는데 전부
"재무제표"로 표시됐다. 검토자가 "이 배당성향 어디서 나왔죠?"라고 물으면 **틀린
답**을 하는 상태였고, 이건 제품의 핵심 주장을 갉아먹는다.

**고친 것 셋**

**① `source_url`과 `verify_url`을 나눈다.**
`https://opendart.fss.or.kr/api/alotMatter.json`은 키가 필요한 JSON이라
**검토자가 클릭해도 아무것도 안 나온다.** 재현에는 그 주소가, 검증에는 DART
뷰어가 필요하다. 한 필드에 뭉치면 둘 중 하나는 반드시 쓸모없어진다.
`dataset`(사람이 읽는 이름)도 함께 넣었다.

**② 파이프라인이 항목별 출처를 살려 넘긴다.** 배선 문제였다. 결과:

| | 이전 | 이후 |
|---|---|---|
| 서로 다른 출처 | **1종** | **6종** |

    19건  재무제표 (주요계정)
    12건  사업보고서 원문 · 주요 제품 및 서비스
     6건  추정 (기준선 · 과거 실적의 기계적 연장)
     5건  정기보고서 · 타법인 출자현황
     3건  정기보고서 · 배당에 관한 사항
     2건  정기보고서 · 최대주주 및 특수관계인 주식소유 현황

**추정치는 공시가 아니라 우리 계산**이라 따로 표시한다 — 원본 공시로 적으면
검토자가 DART에서 없는 것을 찾는다.

**③ 마크다운에 「11. 수치 출처」 표를 붙인다.**
웹에서만 검증되면 **파일로 받는 순간 출처가 사라진다.** 발간물이 파일인 이상
파일 안에 검증 경로가 있어야 한다. 항목 · 값 · 산식 · 출처 · 공시번호(링크).

값은 **플레이스홀더로 넣는다** — 본문과 같은 레지스트리를 거치므로 표와 본문의
숫자가 갈라질 수 없고 G0도 그대로 통과한다. 표가 본문의 일부라 "본문에 등장한
키"를 뽑는 데 순환이 생기므로 **두 번 렌더한다**(1차: 표 없이 → 키 추출,
2차: 표 채움).

**딥링크는 하지 않는다.** 뷰어의 특정 표로 가려면 `dcmNo`/`eleId`가 필요하고
별도 호출·파싱이라 깨지기 쉽다. 대신 **섹션 제목을 명시**한다 — 「사업보고서
원문 · 주요 제품 및 서비스」라고 적으면 검토자가 뷰어 좌측 트리에서 바로 간다.

실측이 잡은 것들

* **G0가 URL과 접수번호를 막았다.** 옳은 판정이라 게이트를 푸는 대신 **좁게**
  넓혔다 — URL 안의 숫자(주장이 아니라 주소)와 14자리 접수번호(금액이면 콤마가
  붙는다). 그 옆의 크기는 여전히 잡힌다(테스트로 고정).
* **섹션 번호 `2.`가 표 셀 한가운데서 맨 정수로 잡혔다.** 목차 번호를 통과시키는
  규칙을 넓히면 그 구멍으로 다른 숫자가 샌다. **제목에서 번호를 뗐다** —
  검토자는 이름으로 찾으므로 잃는 것이 작다.
* **산식의 파이프가 표를 깨뜨렸다** — `|전기|`가 셀 구분자로 해석된다.
  [ff83b3f](.)에서 한 번 밟은 자리를 또 밟았다.
* **역산 시가총액·PER·PBR의 출처가 재무제표로 표시됐다.** 역산 주가에서 파생된
  값이므로 배당공시가 원천이다([D19](#d19)). 잘못 표시하면 검토자가 종가로
  오인할 여지가 커진다.

<a id="d37"></a>
### D37 — 발간 표면을 Next.js + shadcn/ui로 옮긴다 ([D26](#d26) 실행)

[D26](#d26)은 "서버 렌더로 먼저 세우고 `/api/*`는 Next.js가 나중에 그대로
호출한다"고 적어뒀다. 이건 그 계획의 **실행**이지 번복이 아니다. 버린 코드도
없다 — `/api/jobs`·`/api/search`·`/api/reports`가 그대로 프런트의 입구가 됐다.

계기는 사용자 요청("visual template을 바꾸고 싶다")이었고, 목적지는 이미
`surfaces/ra-tool-v0/architecture.md`에 `Next.js 15 (App Router, TypeScript,
Tailwind)`로 적혀 있었다. shadcn/ui는 그 스택의 표준 컴포넌트 모음이다.

**① 정적 익스포트 · 컨테이너 하나.**

Next.js를 별도 서버로 띄우지 않는다. `.arc-store`(추정 이력)가 볼륨에 있어야
하고 corpCode 캐시·LLM 예산이 **프로세스 메모리**에 있어서, 서비스를 둘로
쪼개면 셋 다 깨진다. `output: 'export'`로 빌드해 FastAPI가 `StaticFiles`로
서빙한다. Node는 Docker 빌드 스테이지에만 있고 **런타임에는 없다.**

정적 마운트는 반드시 `/api/*` **뒤에** 등록한다. `/`에 붙으므로 먼저 걸리면
API 요청을 정적 파일 조회가 가로챈다.

**② 노트 본문의 숫자는 여전히 서버가 만든다 — React가 다시 만들지 않는다.**

이 이관에서 가장 중요한 제약이다. `render_html()`이 수치마다
`<span class="num" data-key … data-url>`을 붙여 내보내고, React는 그 문자열을
`dangerouslySetInnerHTML`로 **그대로 주입**한 뒤 `element.dataset`을 읽어
팝오버를 붙인다.

React에서 숫자를 다시 포맷하면 레지스트리를 거치는 경로가 둘이 되고, 그 순간
G0가 지키던 것이 화면에서 무너진다. 차트도 마찬가지다 — `render/charts.py`가
만든 인라인 SVG를 그대로 넣는다([D32](#d32)).

따라서 `web/app/note.css`의 선택자(`.num`, `.num--estimate`, `.note h2/table/
blockquote`)는 **Tailwind 유틸리티로 대체할 수 없다.** 서버가 내보내는 고정
클래스명과 정확히 맞아야 한다. 값만 shadcn 토큰에서 가져온다.

**③ shadcn은 Radix가 아니라 Base UI를 쓴다.**

`base-nova` 스타일은 `@base-ui/react` 기반이다. 팝오버 앵커를 Radix식으로
짜다가 빌드가 깨져서 알았다. 결과적으로는 더 낫다 — Base UI의 Positioner는
`anchor`로 **DOM 엘리먼트를 직접** 받으므로, 서버가 만든 `<span>`을 그대로
넘기면 충돌 회피(화면 밖으로 나가면 뒤집기)까지 맡길 수 있다. 이전 화면은 그
좌표를 손으로 계산했다.

`create-next-app`이 넣는 `web/AGENTS.md`가 "이 버전은 네가 아는 Next.js가
아니다, `node_modules/next/dist/docs/`를 읽어라"라고 경고한다. **지우지 말 것.**
이 발견이 거기서 나왔다.

**④ `--primary`는 무채색으로 둔다 — 화면의 유일한 파란색은 `.num`이다.**

처음엔 기존 파란색(`#2563eb`)을 primary에 넣었다. 그러면 버튼·링크·수치가
전부 같은 색이 되어 **"되짚을 수 있다"는 신호가 묻힌다.** shadcn 기본 무채색을
쓰면 페이지에서 색을 가진 것이 출처 있는 숫자와 의미색 넷(`ok`/`bad`/`warn`/
`est`)뿐이다. 출처 링크도 `primary`가 아니라 `--num`을 쓴다.

**⑤ no-JS 폼 POST를 버린다.**

이전 화면은 JS 없이도 동작했고(`POST /`), `/api/jobs`는 진행 표시를 위한
향상이었다. SPA는 그 성질을 잃는다. 인증 뒤의 내부 도구라 비용이 작다고 보고
포기했다 — **기록해 두는 이유는 이게 의도된 손실이기 때문이다.**

**⑥ 부수 발견: 진행 표시가 죽어 있었다.**

`#prog`·`#steps`·`#elapsed`의 마크업과 CSS는 있는데 **이를 구동하는 JS가
없었다.** 서버 SSE는 완성돼 있고 테스트도 있는데(`web/jobs.py`,
`tests/test_jobs.py`) 브라우저에서 부르는 쪽이 없어서, 폼 POST가 끝날 때까지
그냥 기다렸다. React가 첫 소비자다. 흐름은
`POST /api/jobs` → SSE 구독 → `done` → `GET /api/jobs/{id}/result`.

마지막 조회를 위해 엔드포인트를 하나 더했다. `/api/reports`는 동기라 30~40초를
붙들어 진행 표시를 붙인 이유가 사라진다. 아직 안 끝난 작업에는 409를 준다 —
200에 빈 결과를 주면 화면이 **그걸 결과로 받는다.**

**실측**: 회귀 7종목 전부 게이트 통과, 534 테스트 통과. LG전자 기준 레지스트리
158건 · `.num` 194개 · `data-url` 208개. LLM을 켜면 미검증 레인([D31](#d31))이
blockquote로 갈라지고 그 문단 본문에 숫자가 없다.

**⑦ 출처는 마우스와 키보드 양쪽으로 연다.**

이관 직후에는 마우스로만 열렸다. "숫자를 누르면 출처가 나온다"가 이 제품의
논증인데, 경로가 하나뿐이면 키보드 검토자에게는 그 논증이 **아예 없는 것과
같다.** `render_html()`이 `.num`에 `role="button" tabindex="0"`을 붙이고
화면이 Enter·Space를 받는다. 닫으면 원래 숫자로 포커스를 돌려준다.

마크다운 인라인이라 `<button>`을 쓰면 문단·표 셀 레이아웃이 흔들린다. `span`에
역할만 부여했다. 테스트로 고정했다(`test_number_is_keyboard_reachable`).

**남긴 것**: `src/arc/web/templates/index.html`은 한 릴리스 동안 커밋에
남긴다(롤백 경로). 서빙되지 않는다.

### D38 — RA 도구 표면으로 전환. [D8](#d8)이 기각한 것은 "RA 도구"가 아니라 **"엔터프라이즈로 파는 RA 도구"**였다

**결정**: 목표 제품을 **RA 도구 표면**으로 바꾼다. 판매는 증권사 seat이 아니라 **RA 개인 결제**다. 발간 표면은 중단하지 않되 목적을 바꾼다 — 산출물이 아니라 **RA 접촉의 명분**이다.

**D8을 뒤집는 근거.** D8은 RA 도구를 *"증권사 내부 도구 / 유료 seat / 영업 필요"*로 규정하고 보류했다. 기각의 실질적 근거는 마지막 항목 하나였다 — *"개인 개발자가 증권사 엔터프라이즈 영업을 뚫어야 함"*.

**그 장벽은 지금도 그대로다. 바뀐 것은 장벽이 아니라 판매 경로다.**

RA가 **개인 계정으로 결제해 자기 노트북에서 쓰는 도구**라면 증권사 영업이 필요 없다. 구매 절차도, seat 계약도, 보안 심사도 없다. D8이 테이블에 올린 선택지는 (a) 발간과 (b) 엔터프라이즈 RA 도구 둘뿐이었고, **(c) 개인 셀프서브는 검토되지 않았다.**

즉 D8은 틀린 결정이 아니라 **선택지가 빠진 결정**이었다.

**발간 표면을 목표에서 내리는 근거.** 발간은 *"RA의 업무가 재설계되는가"*를 검증하지 못한다 — **독자가 RA가 아니라 투자자이기 때문이다.** 그리고 [corpus/FINDINGS.md](../corpus/FINDINGS.md)가 결과 기반 품질 정의를 기각한 이상, 발간을 계속해도 *"좋은 리포트란 무엇인가"*에는 답이 나오지 않는다. **그 답은 RA의 반려 사유에 있지 주가 경로에 있지 않다.**

**규제 부담이 내려간다.** 유료 발간은 유사투자자문업 경계에 접근한다 — [D5](#d5)가 무료·일방향을 고른 이유가 그것이다. 반면 **라이선스 보유 전문가가 쓰는 도구**는 컴플라이언스 책임이 사용 기관에 남는다.

**발간 표면 처리 — 폐기가 아니라 용도 변경.** 발간물은 접근 명분이 된다: *"제 도구를 써보시겠어요"*가 아니라 ***"제가 이걸로 만든 리포트인데 봐주시겠어요"***. [D8](#d8) 근거 4번(*"RA 인터뷰를 발간 경험을 갖고 가면 질문의 밀도가 다르다"*)은 그대로 유효하다.

**미리 적는 실패 조건.** RA 인터뷰에서 **5명 중 3명 이상이 "회사가 사줘야 쓴다"**고 답하면 개인 셀프서브 전제가 무너진다. 그때는 D8로 되돌리거나 엔터프라이즈 경로를 다시 연다.

**다음 검증.** 인터뷰에서 직접 묻는다 — *"회사가 사줄 때까지 기다리시겠어요, 본인 카드로 쓰시겠어요? 얼마까지면 그냥 쓰시겠어요?"* **여기서 나온 숫자가 가격이 된다.**

**미구축.** 개인 결제 배관은 없다. 가격도 정해지지 않았다. 둘 다 인터뷰 결과를 입력으로 받는다.

### D39 — 파이프라인을 연다 (블랙박스 → 단계 레일)

화면은 종목코드를 넣으면 30초 뒤 완성본을 뱉는 블랙박스였다. 사람이 개입할
지점이 없고, 기계가 판단 지점까지 대신 지나가 버린다 — [D35](#d35)에서 코스닥
다섯 곳이 글자까지 같은 문장을 받은 게 그 결과다.

**왜 검증기 단독이 아니라 이것인가.** [research/06](research/06-ra-workflow.md)
조사 후 검증기 축을 검토했는데, 파이프라인 **끝**에 있어 RA 하루의 대부분을 못

열면 가치의 단위가 체크당·리포트당·커버리지당 어느 쪽으로 결론 나도 버리지 않는다.

**엔진은 이미 다 알고 있었다.** `ReportResult`가 중간물을 전부 보관하고, 각

`web/app.py::_to_view()`가 절반을 버리고 있었다. **새로 계산한 것이 없다. 드러냈을
뿐이다.**

`StageReport`(key·label·status·summary·checks·registered·note)를 만들고
`build_report`가 단계마다 기록한다. 기록은 **읽기만** 하고 계산 순서에 개입하지 않는다.

**`absent`와 `failed`를 반드시 구분한다.** SK하이닉스에 부문 손익이 없는 것은
정상이고([D33](#d33)이 정확히 거부한다), DART 조회 실패는 결함이다. 같은 색으로
칠하면 검토자가 정상을 결함으로 읽는다.

`registered`(이 단계가 만든 수치 건수)가 파이프라인을 여는 핵심 정보다 — 실측:
삼성전자에서 부문 손익 단계 하나가 **38건**을 만든다.

**단계 목록을 하드코딩하지 않는다.** `vm.stages`에서 오므로 엔진에 단계가 붙으면

* 롯데케미칼: 부문 매출이 **「합계가 매출액과 +8.2% 어긋나 사용하지 않는다」**.

* 롯데케미칼: 지표 12종 · 미확인 계정 `희석주당이익`

**그리고 발간물의 거짓 서술을 하나 잡았다 (수정함).** 파마리서치 리포트가
「2.2 부문 구성」에서 4개 부문(의약품·의료기기·화장품·기타)을 싣고, 같은 문서

### D40 — 보드가 홈이다 (리포트는 지속되는 카드다)

[D39](#d39)로 파이프라인을 열었는데도 흐름은 그대로였다 — **입력 → 대기 → 툭.**
상자를 투명하게 만들었지 상호작용을 바꾸지 않았다. 단계 레일은 영수증이지
작업 흐름이 아니었다.

**측정이 문제를 정확히 보여줬다:**

| | 시간 | 산출 |
|---|---|---|
| 결정론 경로 | **1.4~1.8초** | 검증된 수치 전부 (파마리서치 105건, 출처 포함) |
| + LLM | +30초 | 문장 |

값진 것은 이미 1.5초에 끝나 있고, 30초는 문장 때문이다. **그런데 RA는
생산자다 — 문장은 자기가 쓴다.**

**진짜 원인은 생성물이 일회용이었다는 것이다.** `JobStore`가 메모리에 30분만
들고 있어(TTL) 떠나면 사라졌다. 그래서 화면이 "한 번에 끝내야 하는" 모양일
수밖에 없었다. 리포트가 지속되는 **카드**가 되면 셋이 따라온다 — 나갔다 돌아올
수 있고(RA의 하루는 인터럽트 구동이다), 여러 건이 동시에 뜨고(애널리스트 3~4명
보조·어닝시즌 다종목), 단계가 진행 표시가 아니라 **상태**가 된다.

**칸은 카드가 실제로 멈출 수 있는 자리여야 한다.** 기계가 1.5초에 안 멈추고
통과하면 모든 카드가 마지막 칸에 쌓여 보드가 아니게 된다. 실제로 멈추는 곳:

```
수집됨 → 확인 필요 → 검토 대기 → 발간됨
          ↑ 카드가 실제로 쌓이는 곳
```

「확인 필요」가 이 보드의 존재 이유다 — **다른 데서 못 하는 일(1차 공시 대조)이
거기 있다.** 비어 있으면 우리가 잘한 것이고, 차 있으면 사람이 손댈 곳을 정확히
가리킨다. 「발간됨」은 [D27](#d27)의 그 발간이다 — 이미 있던 사람 게이트가
칸이 됐다.

**칸 배정은 자동이다.** 옮기는 것이 일이 되면 아무도 안 옮기고 보드는 추적기로
전락한다 — 조사에서 RA의 실제 작업 도구는 워드·엑셀이었고, 추적만 하는 도구는
FnGuide WorkWise와 정면 승부다. 대신 사람의 판단은 남긴다: 「확인함」 한 번.

판정은 **기계가 이미 아는 것에서만** 뽑는다(`store/cards.py::attention_reasons`).
게이트 차단 · 단계 실패 · 검산 불일치. **`absent`는 이유가 아니다** — 단일 부문
회사에 부문 손익이 없는 것은 정상이고([D33](#d33)), 그걸 올리면 보드가 늘 빨갛다.

> **열어두되 만들지 않은 것: 수동 카드 이동.** 사람이 임의의 칸으로 끌어 옮기는
> 것은 넣지 않았다. 자동 판정이 실제로 얼마나 틀리는지 보고 붙이는 편이 낫다 —
> 먼저 만들면 옮기는 노동이 생기고, 그 노동이 보드를 죽인다. 붙일 자리는
> `column_for()` 하나다.

**1인 도구를 전제한다.** 「애널리스트 대기」·「준법감시 대기」 같은 사람 대기
상태로 칸을 나누는 안도 검토했는데, 그건 상대가 이 도구를 써야 의미가 있다.
1인에서는 카드를 옮겨도 아무 일이 안 일어나는 메모가 된다. 협업은 나중이다.

`SnapshotStore`를 쓰지 않았다 — 그쪽은 append-only Parquet이고 point-in-time
조회용이라 **변하지 않는** 기록에 맞다. 카드는 칸을 옮기고 확인 표시가 붙는
**변하는** 상태다. `{store}/cards/{id}.json` 하나에 카드 하나를 둔다.

**실측**: 롯데케미칼이 「확인 필요」에 서고 사유가 *"부문별 매출 검산 불일치 —
부문 합계 vs 손익계산서 매출액 +8.1912%"*로 붙었다. 파마리서치는 「검토 대기」로
바로 갔다. 「확인함」이 `attention → review`로 옮긴다.

<a id="d41"></a>
### D41 — 리뷰 루프: 코멘트 → LLM 수정 → diff → 버전

[D40](#d40)까지 만든 것은 전부 **일 주위**였다 — 관찰(D39)과 정리(D40). 정작
**일을 하는 자리**가 없었다. 이 제품에서 사람이 바꿀 수 있는 것은 「추정 가정
덮어쓰기」 텍스트박스 하나뿐이었다.

**루프**: 섹션을 고르고 코멘트를 남기면 → LLM이 그 섹션만 다시 쓰고 →
diff를 보여주고 → 채택하면 v0.1 → v0.2.

**왜 이게 안전한가 — 이 제품만 할 수 있는 보장**

LLM은 `{{num:key}}` 플레이스홀더만 쓰고 **값은 프롬프트에 들어가지도 않는다**
(`narrate.py`와 같은 `catalog()`). 그래서 이 루프가 문서를 고쳐도 **숫자는
구조적으로 바뀔 수 없다.** diff는 문장에만 생긴다.

> *"AI가 내 리포트를 고쳤는데 숫자는 안 건드렸다"* — 이걸 **약속이 아니라
> 구조로** 말할 수 있다. 워드도 노션도 ChatGPT도 못 하는 보장이다.

`RevisionProposal.numbers_unchanged`가 이걸 매번 확인하고, 어긋나면 채택 전에
알린다. 테스트로 고정했다(`tests/test_revise.py`).

**전체가 아니라 섹션만 고친다.** `narrate()`는 문서 전체를 한 번에 만드는데,
리뷰 루프에서 그러면 코멘트 하나 때문에 손대지 않은 문단까지 바뀌어 diff가
의미를 잃는다. **고친 자리만 고쳐야 diff가 논증이 된다.**

**채택 전에 G0를 다시 돌린다.** 막히면 저장하지 않는다 — 게이트를 건너뛰면
리뷰 루프가 불변식을 우회하는 뒷문이 된다. 차단된 본문이 카드에 남으면 다음
수정이 그 위에 쌓인다.

**고칠 수 없는 섹션이 있다.** 디스클레이머(3중 고지가 G0의 발간 조건) · 수치
출처([D36](#d36), 레지스트리가 자동 생성) · 작성 기준 · 산업 배경([D31](#d31),
미검증 레인). 화면에 잠금으로 함께 보여준다 — 왜 못 고치는지도 정보다.

**카드가 되살아나는 문서가 됐다.** 치환 **전** 조립본과 `NumberRegistry.dump()`를
카드에 싣는다. 이게 없으면 카드는 읽기 전용 스냅샷이고 루프가 성립하지 않는다.

**실측** (파마리서치 v0.1 → v0.2, `gpt-5.6-luna` · $0.0015):

```
코멘트: "첫 문장이 결론이 아니라 나열로 시작합니다…"
이전: 2025년 실적은 매출보다 이익이 빠르게 늘어난 운영 레버리지 구간으로, 매출은 …
이후: 이번 실적의 핵심은 매출보다 이익이 빠르게 늘어난 운영 레버리지 구간이었다. 매출은 …
수치 8개 — 변경 없음 · G0 재통과 · v0.2
```

**남은 경계**: G0는 등록 안 된 숫자를 막지만 *"이 코멘트가 요구한 주장이 숫자로
뒷받침되는가"*는 못 본다. "성장성을 더 강조해줘"라고 쓰면 등록된 숫자만 쓰면서도
과장된 문장이 나올 수 있다. [corpus/FINDINGS.md](../corpus/FINDINGS.md)가 남긴
**「좋은 리포트의 정의」 공백**과 같은 자리이고, 이 루프가 그 공백을 처음으로
**추상이 아니라 사례로** 만난다.

### D41 보강 — 편집기가 따라오고, 사람이 직접 고칠 수 있다

초판은 편집 패널이 본문 **맨 위에 고정**돼 있었다. 읽던 자리와 고치는 자리가
멀어서 왕복이 생겼다. 그리고 사람이 할 수 있는 일이 **의견을 주는 것뿐**이라,
"한 단어만 바꾸고 싶다"에도 LLM을 불러야 했다.

**편집기를 화면 아래에 붙여 스크롤을 따라오게 했다.** 제목에 마우스를 올리면
「수정」이 드러나고, 누르면 그 섹션으로 편집기가 열린다. 문서 어디를 읽든 손이
닿는다.

**직접 편집을 열었다 — 그리고 그게 안전하다.**

사람이 원문(플레이스홀더가 살아 있는 마크다운)을 직접 고친다. 저장은 LLM
제안과 **같은 경로**를 타므로 G0가 다시 돈다. 그래서 본문에 숫자를 그냥
타이핑하면 막히고, **왜 막혔는지가 화면에 나온다.**

```
"올해 매출은 5,363억원으로 크게 늘었다"  → 409 차단
   unregistered_number — 미등록 숫자 '5,363' (천단위 구분)
   unregistered_number — 미등록 숫자 '363억' (금액 단위)

"관건은 이 레버리지가 구조적인지다"      → 200, v0.4
```

**이게 직접 편집을 열어도 되는 이유다.** 게이트가 이미 그 자리를 지키고 있었고,
지금까지는 LLM만 그 벽에 부딪혔다. 사람에게도 열어주니 **불변식이 처음으로
눈에 보인다** — "이 문서의 모든 숫자는 출처로 되짚을 수 있다"가 설명이 아니라
경험이 된다.

두 방식이 한 경로를 쓴다: 코멘트든 직접 편집이든 `POST /accept`로 들어가
G0를 통과해야 버전이 오른다. 갈래를 둘로 두면 한쪽이 게이트를 우회한다.

**아직 없는 것**: 숫자를 바꾸는 작업. 지금 두 방식은 **문장만** 바꾼다. 가정
변경·재수집·외부 시세처럼 **수치가 바뀌는 작업**은 diff가 문장이 아니라 숫자에
생기고([D25](#d25)의 revision이 그 diff다), 아직 카드에 연결되지 않았다.

### D42 — 로그인은 Google 하나, 검증은 API가 한다

지금까지 접근 제어는 **공유 비밀번호 하나**(HTTP Basic)였다. 사람마다 자기
종목을 관리하려면 계정이 필요하다.

**제품 결정은 [bridgewright/flightcheck](https://github.com/bridgewright/flightcheck)의
것을 가져왔다 — 문 하나: Google.** 비밀번호도, 도착을 기다려야 하는 메일 링크도
두지 않는다. 그쪽 주석의 표현이 정확하다: *"제품의 유일한 입구를 메일이 와야
열리는 문으로 만들면"* 그 문이 자주 안 열린다.

**구현은 그대로 못 옮긴다.** flightcheck는 Next 서버가 쿠키로 세션을 들고
있다(`@supabase/ssr` · `lib/supabase/server.ts` · `middleware.ts` ·
`/auth/callback/route.ts`). 이 앱은 **정적 익스포트라 Next 런타임이 없다**([D37](#d37)).

| flightcheck | 여기 |
|---|---|
| 서버 클라이언트 · 미들웨어 | 불가 → 브라우저가 세션을 든다 |
| `/auth/callback/route.ts` | 불가 → **클라이언트 페이지**가 코드를 교환 |
| 서버가 쿠키로 검증 | **FastAPI가 JWT 서명을 직접 검증** |

마지막 줄이 flightcheck에 없는 조각이다 — 그쪽은 Supabase가 대신해 주므로
검증 코드가 없다.

**Basic Auth를 같은 커밋에서 지우지 않는다.** 지금 지우면 Supabase 키가 안
꽂힌 동안 서버가 **OpenAI 키를 들고 무방비로 열린다** — `auth.py`가 존재하는
이유가 그것이다. 그래서 설정된 것으로 방식을 고른다:

```
SUPABASE_JWT_SECRET 있음  → 토큰 검증
없고 ARC_PASSWORD 있음    → 공유 비밀번호 (지금 동작 그대로)
둘 다 없음                → 통과 + 경고 (로컬 개발)
```

**Supabase가 배포에서 확인된 뒤에 Basic을 지운다.**

**JWT 모드에서는 화면 껍데기가 공개다.** 로그인 페이지가 그 껍데기 안에 있어서
정적 파일까지 막으면 로그인할 방법이 없다. 데이터는 전부 `/api/*` 뒤에 있으므로
그쪽만 잠근다. Basic 모드는 화면까지 막던 지금 동작을 그대로 둔다 — 갑자기
열면 배포된 주소의 노출 범위가 조용히 넓어진다.

**`EventSource`는 헤더를 붙일 수 없다.** 진행 스트림만 토큰을 쿼리로 받는다.
쿼리 토큰은 서버 로그에 남을 수 있어 일반적으로 피해야 하지만 다른 방법이 없고,
이 경로가 흘리는 것은 단계 이름뿐이다.

**실측** (로컬 JWT 모드):

```
껍데기 /             200   ← 로그인 화면이 열려야 한다
/api/health          200
/api/cards (토큰 X)  401
/api/cards (토큰 O)  200
SSE 쿼리토큰         404   ← 인증 통과 후 "없는 작업"
위조 토큰            401
```

**전제**: HS256 + 프로젝트 JWT 시크릿. Supabase 프로젝트가 비대칭 서명키를
쓰면 JWKS 조회가 따로 필요하다.

**아직 안 한 것**: 카드에 소유자 필드. 지금 카드는 전역이라 로그인해도 모두가
같은 보드를 본다. 사용자 판단으로 나중에 붙인다 — 붙일 자리는 `store/cards.py`의
`Card`와 `CardStore.list()` 하나씩이다.

### D43 — 발간은 초안 작성 폼이 아니라 카드에 있다

RA 두 명분 화면을 보고 나온 지적: **「너무 불친절」**. 화면이 구현의 언어로
말하고 있었다.

| 화면에 있던 것 | 무엇이 문제인가 |
|---|---|
| `받지 못한 것: shares, dividend, audit, workforce, ownership, affiliates` | **영어 필드명이 그대로 샜다** |
| `파이프라인 13단계` | 파이프라인은 우리 말이지 독자의 말이 아니다 |
| `+21` | 무엇이 21건인지 안 쓰여 있다 |
| `사업보고서 원문 (5~8MB) — 7,349,397자` | 글자 수는 RA에게 아무 의미가 없다 |
| `결정론 문장` · `(D27)` | 내부 용어와 결정 번호가 본문에 샜다 |
| **`검토 완료 · 발간`이 `초안 작성` 옆에** | **아직 아무것도 안 만들었는데 「검토 완료」를 누를 수 있었다** |

앞의 다섯은 문구 문제다. 마지막은 **구조 문제**다.

**발간은 읽고 고친 뒤에 하는 일이다.** 폼에 두면 생성과 발간이 한 번에 일어나
검토가 끼어들 자리가 없다 — 생성 ≠ 발간이라고 [D25](#d25)·[D27](#d27)에서
정해 놓고, 화면은 그 둘을 같은 버튼으로 묶고 있었다. [D41](#d41)에서 코멘트로
문단을 고칠 수 있게 만들어 놓고도 **고친 것을 낼 방법이 없었다.**

그래서 `POST /api/cards/{id}/publish`로 옮겼다. 이 엔드포인트는 **다시 생성하지
않는다** — 카드의 현재 `assembled`를 치환해서 낸다. 코멘트로 고친 것도, 직접
편집한 것도 살아서 나간다. 점검을 통과하지 못한 카드는 409로 거절한다.

**단계 이름은 독자가 아는 말로 바꾼다.** `회사 정보 조회`→`회사 확인`,
`LLM 서술 생성 (가장 오래 걸립니다)`→`문장 작성`, `G0 게이트 검증`→`발간 전 점검`,
`파이프라인 N단계`→`자료 수집·검산`, `+21`→`수치 21`. 못 받은 항목도 한글
이름으로 낸다(`shares`→`주식수`).

바꾸지 않은 것: **단계를 숨기지 않았다.** 불친절의 해법은 덜 보여주는 것이
아니라 보이는 것을 읽히게 만드는 것이다 — 무엇을 검산했는지 안 보이면
[D39](#d39)에서 파이프라인을 연 이유가 없어진다.

### D44 — 분기보고서의 전기, 채운 헤더, 숫자마다의 절 링크

삼성물산(028260)으로 실제로 써 보고 나온 지적 넷. 전부 **엔진이 이미 알거나
공시가 이미 주는데 우리가 안 읽은 것**이었다.

**1. 분기보고서에는 전년 대비가 통째로 없었다.**

DART 재무제표 응답의 컬럼 이름이 보고서 종류마다 다르다. 실측:

| 보고서 | 당기 | 전기 | 전전기 |
|---|---|---|---|
| 사업 | `thstrm_amount` | `frmtrm_amount` | `bfefrmtrm_amount` |
| 분기·반기 손익 | `thstrm_add_amount`(누적) | `frmtrm_add_amount` | **없음** |
| 분기·반기 재무상태 | `thstrm_amount` | `frmtrm_amount` | 없음 |

우리는 사업보고서 컬럼만 읽고 있었다. 그래서 분기로 만든 노트는 전기가 전부
비었고, 3개년 차트에 막대가 **한 해에만** 섰다. 어닝 리뷰에서 전년 동기 비교가
빠지면 남는 게 없다.

**누적을 쓴다.** 분기 손익에는 단독 분기와 누적이 함께 오는데, 반기보고서의
`thstrm_amount`는 2분기 단독이라 「반기」라는 이름과 어긋난다. 고른 기간과
숫자의 기간이 같아야 한다. 전전기는 **0으로 채우지 않고** 차트에서 그 해를
뺀 뒤 왜 빠졌는지 적는다.

**2. 부문 구성이 색 막대뿐이었다.**

비중이 감으로만 읽히고 절대 금액은 아예 안 보였다. 정확한 수치는 4.1절 표에
있었지만 화면 두 번을 스크롤해야 나왔다. 차트 바로 밑에 **부문 · 매출 · 비중**
표를 붙인다. 값은 서버가 레지스트리에서 꺼낸 표시 문자열이라 본문의 같은
숫자와 갈라질 수 없다 — 화면이 직접 포맷하면 반올림이 따로 논다.

**3. 헤더 표의 절반이 대시였다.**

`산업 —` · `시가총액 —` · `주가 (—) —`. 다섯 줄 중 셋이 비면 표가 정보를
주는 게 아니라 없다는 사실만 알린다.

* 산업 — DART는 KSIC 코드(`467`)만 준다. **중분류(2자리) 매핑**을 붙였다
  (`data/kr/ksic.py`, 제10차 개정 77개). 모르는 코드는 코드를 그대로 내보내지
  않고 줄을 뺀다 — 빈 칸보다 나쁜 게 뜻 모를 숫자다.
* 시가총액·주가 — 배당에서 역산하는 값이라([D19](#d19)) 늘 있지는 않다.
  없으면 두 줄이 통째로 빠진다.
* 대신 **갖고 있는데 안 쓰던 것**을 올린다: 기준 보고서(접수번호 포함) ·
  회계기준(연결/별도) · 감사의견(감사인 포함).

제목도 고쳤다. 분기보고서로 만든 노트를 「2026년 연간 실적 리뷰」라고 부르고
있었다 — 이제 「2026년 1분기 누적」이다.

**4. 「원문 공시 열기」가 보고서 첫 장으로 갔다.**

삼성물산 사업보고서는 8MB에 목차가 143절이다. 부문 매출 하나 확인하려고
사람이 다시 목차를 뒤져야 했으니, 검증 경로가 있다는 말이 반만 참이었다.

DART 뷰어는 문서 안 위치를 주소로 받고(`report/viewer.do?rcpNo=…&dcmNo=…
&eleId=…&offset=…&length=…`), 그 좌표가 `dsaf001/main.do`의 목차 트리에 그대로
박혀 있다. 목차를 한 번 읽어 두면 **수치마다 자기 절로 가는 링크**가 나온다.
실측 138건이 연결됐다:

```
재무제표 (전체계정)          → 2. 연결재무제표
사업보고서 원문 · 영업부문      → 3. 연결재무제표 주석
정기보고서 · 배당에 관한 사항   → 6. 배당에 관한 사항
정기보고서 · 최대주주 …        → VII. 주주에 관한 사항
```

**못 찾으면 그대로 둔다.** 첫 장으로 가는 링크는 불편할 뿐이지만, 엉뚱한
절로 가는 링크는 틀린 주장이다. 추정치처럼 원문에 없는 수치는 아예 보내지
않는다.

### D45 — 최근 기사를 붙인다. 단, 미검증 레인의 규칙 그대로

「AI를 활용해 최근 기사도 반영하면 더 풍성해지지 않을까」에서 나왔다. 열린
질문 [Q11](#열린-질문)이 정확히 이것이었다 — *산업 서사 레인을 검증 가능하게
만들 수 있는가.*

**답: 검증 가능해지지는 않는다. 되짚을 수 있게는 된다.**

지금 산업 배경 레인의 근거는 **모델의 기억**이다. 틀렸는지 확인할 방법이 없다.
기사는 다르다 — 매체·날짜·링크가 붙으므로 독자가 원문으로 갈 수 있다. 그렇다고
우리가 검산한 것은 아니다. 이 둘은 구분해야 한다.

그래서 **[D31](#d31)을 완화하지 않는다.** 기사 레인도 숫자를 쓰지 못한다.
바뀌는 것은 근거의 종류이지 검증의 유무가 아니다.

**세 겹으로 막는다.**

1. 프롬프트에 넣기 전 스니펫의 숫자를 `mask_numbers()`로 가린다. LLM이 베낄
   유혹을 애초에 없앤다 — 안 가리면 베끼고, G0가 막고, 재시도만 낭비한다.
2. 나온 문단에 숫자가 하나라도 있으면 문단을 **버린다**(산업 배경과 같은 규칙).
3. **기사 제목의 숫자도 가려서 싣는다.** 「5,000억원 규모 수주」를 그대로
   옮기면 독자는 그걸 우리가 확인한 값으로 읽는다. `⟨수치⟩억원 규모 수주` +
   링크가 정직하다.

가림과 탐지가 **같은 화이트리스트**를 쓰므로 가린 텍스트는 게이트를 통과하는
것이 보장된다(`test_masking_is_gate_safe_by_construction`).

**두 미검증 레인을 한 절에 모았다.** `## 0. 공시 밖 배경` 아래 `0.1 산업 구조`
· `0.2 최근 이슈`. 경고 문구를 두 번 띄우면 두 번째부터 안 읽힌다. 두 소절 다
`revise.py`의 `_LOCKED`에 넣었다 — 검산할 수 없는 문단을 LLM이 또 만지면
무엇이 어디서 왔는지 추적이 끊긴다.

**LLM이 꺼져 있으면 검색도 꺼진다.** 스니펫을 문단으로 만드는 게 이 레인의
전부라, 문장을 안 쓰면 링크 목록만 남는다. 화면에서도 체크박스가 종속된다.

**라벨을 「문장까지 작성」에서 「AI로 서술 작성」·「AI로 최근 기사 반영」으로.**
누가 쓰는지가 안 보이면 RA는 이 도구가 무엇을 대신하는지 판단할 수 없다.
안내문에 *"AI는 문장만 쓰고 숫자는 코드가 만듭니다"*를 붙였다 — 이 제품의
전제인데 화면 어디에도 안 쓰여 있었다.

**키가 없으면 못 한다고 쓴다.** `NAVER_CLIENT_ID`/`SECRET`이 비어 있으면
`/api/health`가 `news_key: false`를 내고 체크박스가 이유와 함께 잠긴다.
누를 수 있는데 아무 일도 안 일어나면 사용자는 고장으로 읽는다.

**아직 안 한 것**: 기사 톤이 리포트 톤을 오염시키는지 측정하지 않았다. 국내
경제지 기사는 홍보성이 강해 「호실적」·「기대」가 문단에 스밀 수 있다. 키를
받아 실측한 뒤 프롬프트를 조일 자리다.

### D46 — 직전 발간 노트 대비 무엇이 달라졌는가

RA가 같은 종목의 새 분기 노트를 열고 가장 먼저 묻는 것 — *지난번 내 노트에서
뭐가 바뀌었지.* [D25](#d25)가 *"조정 방향과 시점은 추정치 자체만큼 중요한
기록"*이라고 정해 놓고, 구현된 것은 **추정치 한 종류뿐**이었다. 부문 구성이
바뀌어도, 최대주주 지분이 움직여도, 감사의견이 달라져도 화면에 표시가 없었다.

레지스트리에 이미 다 있다. **발간할 때 통째로 남겨 두면** 다음 발간에서
비교가 된다(`store/notes.py`). 발간 시점인 이유는 [D27](#d27)과 같다 —
만지작거린 미리보기까지 세면 「직전」이 무엇인지 알 수 없다.

**키는 라벨을 정규화해서 맞춘다.** 레지스트리 키에는 기간이 박혀 있어
(`revenue_2026a`) 그대로 비교하면 매 분기 전부가 「신규」가 된다. 실적은
연도를 떼고(`매출액`), 추정은 남긴다(`매출액 (2026E)`) — 같은 목표연도의
추정이 어떻게 움직였는지가 핵심이라서다.

#### 「신규」·「사라짐」은 내지 않는다 — 세 번 시도해서 세 번 다 쓰레기

| 비교 | 결과 |
|---|---|
| 연간 노트 vs 분기 노트 | 분기에 없는 EBITDA 마진·부문 이익·배당이 전부 「사라짐」 |
| 1분기 vs 1분기 | 2025년은 사업보고서가 나와 주식수·배당·지분이 실렸고 2026년은 아직 안 나와서, 또 전부 「사라짐」 |
| 추정 | 2025 노트는 2026을, 2026 노트는 2027을 세우니 매번 신규 겸 사라짐 |

셋 다 **회사에 생긴 일이 아니라 그 시점에 공시가 얼마나 나와 있느냐**의
문제다. 항목의 유무로는 사건을 판정할 수 없다. 구조 변화는 `texts`
(감사의견·감사인·보고부문 구성)가 「변경」으로 잡는다 — 양쪽 노트에 다 있을
때만 비교하므로 커버리지에 안 흔들린다.

**기간이 다르면 실적 금액도 비교하지 않는다.** 매출이 40조에서 10조로
「줄어」 보이는 것은 분기가 짧아서다. 비율·구성비·지분과 연간 기준 추정만
비교하고, 왜 뺐는지 화면에 적는다.

#### 저장소 버그 둘 (같이 고쳤다)

* **같은 날 두 번 저장하면 앞엣것이 사라졌다.** 스냅샷 파일 이름을
  `snapshot_at`으로 짓는데 발간 스냅샷은 시각을 **발간일**로 찍는다
  (point-in-time). 하루에 두 종목을 발간하면 이름이 같아져 덮어썼다 —
  실측으로 삼성물산 지문이 파마리서치 것에 지워졌다. 시각은 의미이므로
  그대로 두고 파일 이름만 겹치지 않게 했다(`__1`). **이 버그는 추정 이력
  (D25)에도 있었다** — 종목 둘을 다루는 순간 revision 추적이 끊겼다.
* **`read_as_of`는 마지막 스냅샷 하나만 본다.** 종목별 이력에는 맞지 않아
  `read_history`를 새로 뒀다. as-of 재현(백테스트)에는 여전히 전자가 맞다.

### D47 — 기사는 걸러서 넣는다. 매체 화이트리스트는 실측으로 뒤집혔다

[D45](#d45)에서 기사 레인을 붙였는데, 「삼성물산」 한 번 검색하면 100건이 온다.
그대로 넣으면 프롬프트 절반이 같은 보도자료다.

**네이버 검색 API가 이관됐다.** 2026-07-31부터 개발자센터에서 신규 발급이
막히고 **NAVER API HUB**(NCP)로 옮겨졌다. 응답 본문은 같고 주소와 인증
헤더만 다르다 — 어댑터가 양쪽을 다 안다(`NAVER_API_MODE`, 기본 `hub`).

#### 실측으로 뒤집힌 것 셋

**1. 매체 화이트리스트를 하드 필터로 쓰면 안 된다.** 통신사·경제지만 남기려
했는데, 삼성물산 100건에서 제목에 회사명이 있는 11건이 **전부 목록 밖
매체**였다. AND로 걸면 0건이다. 정작 목록 안 매체가 준 것은 「코스피 급락」·
「폭염 건설현장 점검」이었다. **매체는 관련성을 대신하지 못한다.** 관련성은
「제목에 회사명이 있는가」가 가른다. 매체 목록은 대신 **중복 묶음의 대표를
고르는 데** 쓴다 — 같은 사건을 열 곳이 쓰면 연합뉴스 것을 남긴다.

**2. `sort=date`는 대형주에서 오늘 하루치만 준다.** 삼성물산은 하루 100건이
넘는다. 3개월 창을 쓴다면서 실제로는 오늘만 보고 있었다. `date`는 제목매치
11/100, **`sim`은 80/100**. 날짜는 필터가 상한으로 자른다.

**3. 한국어 제목은 단어 겹침으로 못 묶는다.** 「홈닉 세차·반려동물 케어까지」와
「건설부문, 홈플랫폼 '홈닉' 생활편의 서비스 4종 출시」는 겹침이 0.4다. 어미와
어순이 매체마다 다르기 때문이다. 대신 상투어(출시·확대·발표…)를 걷어내면
**같은 사건은 같은 고유명사를 쓴다** — `홈닉`, `자이너`. 사건 토큰이 **하나만**
겹쳐도 7일 안이면 같은 사건으로 본다. 2개 기준은 16건에 홈닉이 4건 남았고,
1개 기준은 11건에 1건으로 접혔다.

#### 증권사 리포트 요약은 반드시 막는다

「IBK證 "…목표가 50만원"」·「…성장 사이클 진입-NH」가 통과하고 있었다.
**남의 목표주가를 우리 노트에 싣는 셈**이라 [D4](#d4)에 정면으로 걸린다.
매체가 증권사를 주어로 쓰는 형태와 제목 끝에 출처를 다는 형태를 둘 다 막는다.

#### API 호출 방어

* **종목당 1회.** 100건을 한 번 받아 여기서 거른다. 페이지를 넘기지 않는다.
* **종목·날짜당 캐시.** 가정을 바꿔가며 다시 계산하는 게 이 도구의 일이라,
  캐시가 없으면 호출이 그 횟수만큼 는다.
* **LLM이 꺼져 있으면 검색도 안 한다.** 문단을 못 만들면 링크 목록만 남는다.

#### 검색어는 **법인명이 아니라 상장 종목명**이다

DART `corp_name`은 영문을 한글로 음차해 둔다 — `에이치디현대중공업(주)` ·
`에스케이하이닉스(주)` · `(주)엘지에너지솔루션`. 기사는 `HD현대중공업` ·
`SK하이닉스` · `LG에너지솔루션`으로 쓴다. 법인명으로 검색하면 거의 안 걸린다
(실측: HD현대중공업 1건).

`company.json`이 `stock_name`을 함께 주므로 `Company.short_name`에 싣고,
**바깥 세상과 맞출 때는 그쪽을 쓴다.** 노트 제목·헤더는 정식 법인명 그대로다.
법인 표기(`(주)`)도 뗀다 — `(주)파마리서치` 3건, `파마리서치` 10건.

#### 게이트가 매체 도메인에 막혔다

기사 표의 「매체」 칸이 모르는 곳은 도메인을 쓰는데, `viva100.com`의 `100`이
미등록 숫자로 잡혀 **발간이 통째로 막혔다.** G0는 이미 URL을 「주장이 아니라
주소」로 허용하고 있었다 — 도메인만 빠져 있었다. 알려진 TLD로 끝나는 호스트명을
같은 이유로 허용한다. 금액은 그 모양이 될 수 없다.

### D48 — RA는 백지에서 시작하지 않는다: 기존 노트를 올린다

*"새로운 종목이 아닌 이상, 기존 종목이면 그들도 기존에 작성했던 문서를 갖고
있지 않을까? 그걸 업로드하면 우리가 md로 고쳐서 그걸 기반으로…"*

그동안 「과거 리포트」는 **데이터 확보가 막혀** 보류돼 있었다. 사실 우리가
구할 게 아니라 **사용자가 이미 갖고 있다.** 게다가 자기 문서라 저작권이
깨끗하고, 남의 리포트보다 값지다 — 자기 하우스 포맷, 자기 직전 추정, 자기 관점.

**들어오는 것도 마크다운으로 통일한다.** 이 제품이 내는 것이 이미 마크다운이라
([D36](#d36)) 비교·편집·발간이 한 종류의 문서로 정리된다. PDF를 PDF로 들고
있으면 아무것도 못 한다. 참고한 것은
[engineering.fractional.ai](https://engineering.fractional.ai/using-mcps-with-evals)의
「View as Markdown」 — 같은 주소에 `.md`를 붙이면 원문이 나온다. 우리도
`GET /api/cards/{id}.md`를 그렇게 뒀다.

#### 쓰임새는 둘이다 (숫자는 어느 쪽이든 본문에 안 들어간다)

1. **직전 노트 기준선** — [D46](#d46)의 비교 기계에 그대로 물린다.
   「당신은 2026 매출 12.4조를 봤는데 공시 기준선은 11.2조다」
2. **구성 따라 쓰기** — 그 노트의 섹션 차례로 우리 초안을 낸다.
   하우스 스타일이 있는 곳에서는 이게 채택을 가른다.

**업로드 문서의 숫자는 본문 출처가 못 된다.** 우리가 검산한 값이 아니다 —
기사 레인([D45](#d45))과 같은 취급이다. 그 선을 넘으면 「본문 숫자는 전부
레지스트리를 거친다」는 전제가 무너지고, 이 제품이 파는 것이 없어진다.

추정치 추출은 **LLM으로 한다.** 하우스마다 표가 달라(「2026F 매출액」·
「26E Revenue」·「매출(십억원)」) 정규식으로는 하우스 수만큼 규칙이 필요하다.
LLM은 표를 잘 읽고, **여기서 나온 숫자는 본문에 안 가므로** 불변식을 건드리지
않는다. 틀려도 비교 패널이 이상해질 뿐이다. 실측(HMM/iM증권): 목표주가
21,000원 · Hold · 3개년 매출·영업이익·순이익 정확히 추출.

**차례는 LLM 없이 뽑는다** — 제목은 이미 구조다. LLM이 없거나 실패해도
「구성 따라 쓰기」는 성립한다.

#### PDF 추출은 되는가 — 실측

무작위 200편에서 **추출 실패 0건**. 「한글 0%」로 잡힌 2편은 깨진 게 아니라
영문 리포트였다.

다만 **폰트 CMap이 어긋난 문서가 있다.** 같은 종목·같은 분기인데 한 편은
멀쩡하고(「1분기 영업이익은 전년 대비 68% 증가한 381억원」) 다른 편은
`ۓΌ("ࣄۓ݌ľ ηԮࠒҀғ`다. 탐지기를 붙였는데 **한 번 틀렸다**: 처음에는
「0x2500 미만은 통과」로 짜서 통째로 놓쳤다 — 깨진 글자가 아랍(U+06xx)·
데바나가리(U+09xx)로 떨어지는데 그게 전부 통과했다. 허용 영역을 명시로 바꾸니
깨진 문서 0.269, 정상 문서 ≤0.002, 무작위 80편 오탐 0건으로 갈렸다.

**부분적으로 깨진 문서는 못 잡는다** — 2009년 리포트의 「매춗액」·「달성핚」은
여전히 정상 한글 음절이라 통계로 안 갈린다. 그래서 **변환 결과를 사람이 보고
넘기는 흐름**이 필요하다(smallpdf가 하는 방식). 자동 판정을 믿게 만들면
조용히 쓰레기가 들어온다.

**한글(HWP)은 아직 못 읽는다.** 표준 파서가 없고 포맷이 둘(hwp/hwpx)이다.
「PDF로 내보낸 뒤 올려 주십시오」라고 말한다 — 못 하는 것을 되는 척하는 것보다
낫다.

#### 관통 실측 (HMM 011200 · iM증권 2025-05-19 리포트를 직전 노트로)

```
읽어낸 추정   2025  매출 10.65조 · 영업익 1.68조 · 순익 2.01조
             2026  매출 10.37조 · 영업익 1.13조 · 순익 1.53조
             2027  매출 10.50조 · 영업익 1.23조 · 순익 1.62조
차례         HMM (011200) / 공적 자금 투자의 모범 사례 / Hold (Maintain) / …

비교 기준: 업로드한 노트 대비 · 업로드 문서의 값은 우리가 검산하지 않았습니다
  증가  매출액 (2026E)     10조 3,730억원 → 12조 6,537억원   +22.0%
  증가  영업이익 (2026E)     1조 1,330억원 →  1조 6,976억원   +49.8%
  증가  당기순이익 (2026E)    1조 5,340억원 →  2조 1,827억원   +42.3%
```

**발간 이력이 없어도 「직전 대비」가 채워진다.** 지금까지는 우리 도구로 두 번
발간해야 비교가 나왔는데, 처음 쓰는 사람에게는 그게 영영 비어 있었다.

**목표주가 추출은 흔들린다** — 같은 문서에서 한 번은 21,000원을 읽고 한 번은
못 읽었다. 비교 축이 아니라 참고 표시라 그대로 두지만, 값이 없을 때 없다고
말하는 것 말고는 믿을 게 없다.

### D49 — 보드가 집이고, 생성은 상주 패널이 아니라 행동이다

*"새로 보고서를 발간할 때는 왼쪽에 항상 있는 게 아니라, 첫 화면은 칸반 같은
보고서들이 보이는 형태이고… 있으면 우측 상단에 새 글쓰기 아이콘으로"*

맞다. 생성 폼이 왼쪽 열에 상주하던 것은 **「입력 → 대기 → 툭」 시절의
잔재**다. 카드가 지속되는 객체가 된 순간([D40](#d40)) 보드가 집이어야 했는데
레이아웃이 안 따라갔다. 화면 320px을 늘 차지하면서 하는 일은 「가끔 누르는
버튼」이었다.

| | 전 | 후 |
|---|---|---|
| 첫 화면 | 폼(왼쪽 상주) + 보드 | **보드 전폭** |
| 생성 | 늘 열린 폼 | 우상단 **「+ 새 노트」** → 모달 |
| 카드 0건 | 빈 칸반 + 「왼쪽에서 생성하면…」 | **큰 CTA 하나** — 처음 온 사람에게 보여줄 것은 빈 칸반이 아니라 할 일이다 |

#### 딸려 나온 것 — 단계 레일은 카드 것이다

레일이 **폼 안에** 있었다. 그래서 두 건을 돌리면 **마지막 것의 진단만** 보였다
— 먼저 돌린 카드는 무엇을 검산했는지 볼 방법이 없었다. 레일은 원래 카드의
속성인데(카드 `vm.stages`에 이미 들어 있다) 붙은 자리가 틀렸던 것이다.
카드 화면으로 옮겼다.

옮기면서 회귀가 하나 생겨 같이 막았다: 폼이 모달이 되면 **생성 30초 동안
진행 표시가 어디에도 없다**(보드에는 「생성 중…」 한 줄뿐). 그래서 제출하면
**그 카드를 바로 연다** — 레일이 살아 있는 채로 보이고, 끝나면 같은 자리에
본문이 온다. 이를 위해 `POST /api/jobs`가 `job_id`와 함께 `card_id`를
돌려주도록 했다.

**같은 함정을 세 번째로 밟았다** — effect 본문에서 바로 `setState`하면
연쇄 렌더가 난다(`react-hooks/set-state-in-effect`). 비동기 뒤로 넘겨야 한다.

### D50 — 시작 화면은 「이어쓰기 / 새로 시작」 두 갈래다

[D49](#d49)에서 생성을 모달로 옮겼는데, 모달 안이 여전히 폼 하나였다. 그런데
[D48](#d48)로 업로드가 붙으면서 **시작하는 방법이 둘**이 됐다 — 커버 중인
종목을 이어 쓰는 것과, 새 종목을 여는 것. 둘은 같은 폼의 옵션이 아니라
**다른 시작**이다. 실제로 RA가 하는 일의 대부분은 앞엣것이다.

```
리포트 초안 작성
┌──────────────────────┬──────────────────────┐
│ 직전 리포트에서 이어쓰기  │ 새 종목으로 시작        │
│ PDF · DOCX · MD       │ KOSPI · KOSDAQ · KONEX │
└──────────────────────┴──────────────────────┘
        ↓ 올림
   올린 문서를 확인하십시오
   HMM (011200) · KOSPI
   에이치엠엠(주)
   읽어낸 구성: HMM (011200) / 공적 자금 투자의 모범 사례 / …
        ↓ 「HMM로 이어쓰기」
   초안 작성 (종목이 채워진 폼)
```

**올리자마자 쓰지 않는다.** 먼저 읽어서 「어느 회사인가」를 되돌려 준다.
종목코드를 다시 치게 하면 업로드가 편의가 아니라 **일이 하나 는 것**이다.

#### 종목코드를 문서에서 읽는다 — 실측 92%

국내 리포트는 첫 장에 「종목명 (123456)」을 거의 반드시 쓴다. 다만 리포트에는
전화번호·사업자번호·날짜가 6자리로 널려 있어서 모양만 보면 엉뚱한 것을 집는다.
**DART 고유번호 표(3,981종목)에 있는 코드만** 받고, 괄호 표기를 먼저 본다.

코퍼스 150편으로 쟀다(파일명에 정답이 있다):

| 창 | 적중 | 오답 | 못 찾음 |
|---|---|---|---|
| 앞 2,000자 | 82% | 4% | 13% |
| **앞 4,000자** | **92%** | **4%** | **3%** |
| 앞 8,000자 | 92% | 4% | 3% |

4,000자에서 포화한다. **오답 4%가 남으므로 화면이 확인을 받는다** — 읽어낸
회사·시장·법인명과 변환 원문 일부를 함께 보여 주고 사람이 넘긴다. 조용히
통과시키면 엉뚱한 회사의 초안이 나온다.

#### 문구

「새 노트」·「노트 만들기」를 **「리포트 초안 작성」**으로. 이 도구가 만드는
것은 메모가 아니라 리포트 초안이고, RA에게 「노트」는 다른 것을 뜻한다.

### D51 — 칸반을 셋으로 줄이고, 확인 사유를 RA의 말로

*"저 4단계가 맞는지 모르겠어. 수집됨은 사실 등록하면 잠깐 있다가 확인 필요로
넘어오잖아. 사실, 확인 필요에서 적힌 내용도 너무 AI스럽고…"*

맞다. **저 4칸은 RA 워크플로에서 나온 게 아니라 우리 파이프라인의 내부
상태**(`running`/`attention`/`review`/`published`)를 그대로 옮긴 것이었다.

#### 조사 — RA는 발간 권한이 없다

해외 리서치 관리 시스템(RMS)의 표준 흐름은 이렇다
([ANALEC](https://www.analec.com/articles/equity-research-publishing-software) ·
[theinkorporated](https://www.theinkorporated.com/insights/equity-research-reports-pre-publication-review/)):

```
애널리스트 초안 → 어소시에이트/에디토리얼 → Supervisory Analyst 승인
                                        → 컴플라이언스 → 제작 → 배포
```

국내도 같다. [WorkWise](https://corp.fnguide.com/Service/SolutionService)는
*"보고서 작성 시점부터 최종발간단계까지 Chinese Wall 및 승인 절차"*를 걸고
부서장 승인 뒤 매매제한·홈페이지 공시·이메일을 자동 연계한다.
[금투협 IR·조사분석 업무처리강령](https://law.kofia.or.kr/service/law/lawFullScreenContent.do?seq=324&historySeq=1134)은
조사분석자료를 **공표 전 심의** 필수로 못박는다.

**그래서 종착점이 「발간」인 것은 구조적으로 틀렸다.** RA(어소시에이트)는
승인권자가 아니다. RA의 종착점은 **「넘김」**이다.

#### 넷 → 셋

| 옛 칸 | 어떻게 됐나 |
|---|---|
| 수집됨 | **칸이 아니다.** 1.5초 머무는 곳은 칸이 아니라 카드 위 스피너다 |
| 확인 필요 | **칸이 아니라 속성이다.** 검토 중인 카드가 확인이 필요할 수도 아닐 수도 있는데, 다른 칸에 두면 「검토는 하는데 게이트가 막힌 카드」가 갈 곳이 없다 → **배지** |
| 검토 대기 | → `검토 중` |
| 발간됨 | → `넘김` |

```
초안              검토 중            넘김
기계가 만들어 놓은 것   읽고 고치는 중      확정해서 내보낸 것
```

**옮기는 것은 사람이다.** 예전에는 게이트 통과 여부로 자동 판정했는데, 그러면
칸이 「기계의 상태」를 말하지 「내가 어디까지 봤는가」를 말하지 않는다. 어닝시즌에
여덟 종목이 굴러갈 때 RA가 알고 싶은 것은 후자다
(`research/06-ra-workflow.md`: **애널리스트 3~4명 보조 · 여러 종목 동시**).

#### 같은 보고서로 두 번 만들지 않는다

RA는 한 종목에 초안 두 개를 동시에 굴리지 않는다. 보드에 같은 카드가 둘이면
어느 쪽이 최신인지 알 수 없고, 고쳐 놓은 쪽을 버리게 된다. 이미 있으면
409와 함께 그 카드 id를 주고, 화면은 **그것을 연다**. 넘긴 뒤에는 다시 만들 수 있다.

#### 확인 사유를 다시 썼다

옛 문구:

```
G0 차단 1건 — 발간할 수 없습니다
부문별 매출 검산 불일치 — 부문 합계 vs 손익계산서 매출액 -31.8011%
발간 전 점검 실패 — 차단 1건 — 발간할 수 없습니다.
관점 분석 검산 불일치 — 집중 부문 매출과 지분 구조를 확인하지 못해
                     무엇에 기대고 있는지 가리지 못했다.
```

문제가 넷이었다. `G0`는 내부 코드명이고, 1번과 3번은 **같은 사건을 두 번**
말하고, 소수점 넷째 자리는 사람이 읽는 숫자가 아니고, 마지막 줄은 시스템이
자기 사정을 문학적으로 말한다. 그리고 전부 **「그래서 뭘 해야 하나」가 없다.**

지금:

```
내보낼 수 없습니다 — 본문에 출처 없는 숫자가 1건 있습니다
부문별 매출 합계가 32% 어긋납니다 — 사업보고서 부문 표를 확인하십시오.
                                내부거래가 섞이면 합계가 어긋납니다.
```

**저장하지 않고 읽을 때 계산한다.** 생성 시점에 굳혀 두면 문구를 고쳐도 이미
만든 카드에는 영영 옛말이 남는다 — 실제로 이번에 밟았다.

#### 여전히 미검증

이 3칸도 근거가 반쪽이다. 「RA는 발간 못 한다」는 조사로 확인됐지만, **축이
진행 단계인지 애널리스트별인지**는 모른다. 3~4명을 보조한다면 「김애널 3건 /
박애널 5건」이 더 쓸모 있을 수 있다. `research/06-ra-workflow.md` §8의
인터뷰 질문에 답이 있고, 그 인터뷰는 아직 안 됐다.

### D52 — 「불일치」와 「자료 없음」은 다르다

*"삼성전기 주식수/배당/지분이 틀리다고 나오는데, 어딜 보고 어떻게 고쳐야 할지를
모르겠네"* — 카드에 이렇게 떠 있었다:

```
주식수·배당·지분 등 — 0/6종                    수치 3
  발행주식 − 자기주식 = 유통주식        불일치
  받지 못한 것: 주식수, 배당, 감사의견, 인력, 최대주주 지분, 타법인 출자
```

**6종을 하나도 못 받았는데 검산이 「불일치」다.** 자료가 없으면 검산 결과도
없어야 한다. 원인은 `ValuationSet.shares_reconciled`의 **기본값이 `False`**인
것이었다 — 주식수를 못 받으면 그 값이 그대로 남아 어긋난 것처럼 보인다.
[D39](#d39)가 단계 수준에서 정한 `absent`/`failed` 구분이 **검산 항목 수준에는
없었다.**

RA는 있지도 않은 불일치를 찾으러 간다. 이게 신뢰를 깎는 종류의 오류다 —
한 번 헛걸음하면 다음부터 경고를 안 믿는다.

**셋을 고쳤다.**

1. **자료가 없으면 검산 항목을 만들지 않는다.** `info.shares is None`이면
   그 줄 자체가 없다.
2. **분기·반기의 0/6종은 `absent`다.** 이 6종은 사업보고서에만 실린다 —
   정상 부재를 `partial`로 두면 카드가 늘 「확인 필요」가 된다. 문구도
   *"분기·반기보고서에는 원래 없습니다"*로 명시한다.
3. **어긋났을 때는 숫자를 보여준다.** 「불일치」 한 마디로는 어디를 볼지
   알 수 없다:

```
전:  발행주식 − 자기주식 = 유통주식        불일치
후:  77,600,680 − 2,053,430 = 75,547,250          (일치할 때도 숫자를 보여준다)
     100,000 − 5,000 = 90,000 (계산상 95,000, 차이 +5,000주)
```

실측 결과:

| | 전 | 후 |
|---|---|---|
| 삼성전기 2026 1분기 | `partial` · 「불일치」 · 카드에 경고 | **`absent`** · 검산 없음 · **경고 없음** |
| 삼성전기 2025 사업 | `ok` · 「일치」 | `ok` · **`77,600,680 − 2,053,430 = 75,547,250`** |

### D54 — 재무제표 3종과 3개년: 받아놓고 안 쓰던 것

그래서 붙인 것: 손익 3개년 + **4.1 재무상태** + **4.2 현금흐름**.

(벤치마크: `2024A 2025A 2026F 2027F`). **규칙과 관행이 같은 답을 가리켰다.**

#### 아직 못 하는 것

* **PER/PBR/EV·EBITDA 시계열** — 주가가 필요하다. `KRX_API_KEY`가 비어 있어

  있는 회사만이다

### D55 — 모델은 대체하지 않고 먹인다 (방향)

동료 인풋: *"예전에는 데이터 수집/정리, **모델 관리(업데이트)**, 고객사
리퀘스트 처리, **리포트 내에 차트 그리기**가 주요 업무 카테고리였던 것 같은데"*

셋 중 둘은 우리가 이미 「누락」이라 적어둔 것이고([research/06](research/06-ra-workflow.md)
§5·§7), **「모델 관리」는 열린 질문 [Q2](#열린-질문)(가설 H1) 그 자체**다.
동료가 카테고리로 꼽았다는 것은 H1을 지지하는 신호다.

**그리고 [D54](#d54)의 측정과 맞물린다.** 벤치마크의 5쪽이 재무제표 4종
× 4개년인데, 그건 **RA가 관리하는 엑셀 모델의 출력**이다. 「표를 채운다」와
「모델을 갖는다」는 같은 말이다. 지금 우리는 노트 생성기라 **모델의 부산물만
만들고 있을 수 있다.**

**선례**: [Daloopa](https://daloopa.com/benefits/model-updates)가 정확히 이
제품이다 — 공시를 구조화해 **애널리스트의 기존 엑셀 모델을 한 번 클릭으로
갱신**하고, 모든 숫자에 원문 하이퍼링크가 붙는다. 설계 철학이 같다:
**모델을 대체하지 않고 먹여준다.** 그리고 그들은 웹앱이 아니라 **Excel
애드인**을 만들었다 — 모델이 애널리스트 PC의 엑셀에 살기 때문이다.

**붙는 방법 셋, 그리고 왜 파일부터인가**

| | 어디서 되나 | 비용 |
|---|---|---|
| **① 파일 in/out (xlsx·docx)** | **어디서나** | 낮음 |
| ② 구글 시트 연동 | 그 증권사가 워크스페이스를 쓸 때만 | 중간 (로그인은 이미 구글, D42) |
| ③ Excel 애드인 | 어디서나 | 높음 |

**②가 막힐 수 있다.** 금융회사는 내부망·외부망을 물리적으로 분리해야 하고
([전자금융감독규정](https://www.fsc.go.kr/no010101/77672)) SaaS가 이와 충돌해
왔다. 2024-08 「금융분야 망분리 개선 로드맵」으로 완화 중이고 구글 워크스페이스
도입이 "기대" 단계지만, **개별 증권사가 실제로 쓰는지는 다르다.** 리서치센터는
조사분석자료를 다뤄 더 보수적일 수 있다.

**①부터 간다.** ②·③으로 가더라도 「어떤 표를 어떤 모양으로」가 먼저 정해져야
하고, 지금 가장 큰 갭은 여전히 데이터다([D54](#d54)의 「아직 못 하는 것」).

**인터뷰에서 이 둘이 ①/②/③을 가른다**: *회사에서 구글 워크스페이스나
MS365를 쓰는가, 망분리라 막혀 있는가* / *모델은 엑셀인가, 그 엑셀은 내 PC인가
공유 드라이브인가 회사 시스템인가.*

### D56 — 엑셀 내보내기: 숫자가 숫자여야 한다

[D55](#d55)에서 정한 「파일부터」의 첫 걸음. 모델은 엑셀에 살고, 새 공시가
나오면 그 숫자를 모델에 옮겨 적는 것이 반복 노동이다. 우리는 그 숫자를
**검산까지 마친 채로** 갖고 있다.

**마크다운이 아니라 레지스트리를 읽는다.** 노트의 「11조 3,145억원」은 사람이
읽는 문자열이라 모델에서 쓸 수 없다. `NumberEntry.value`가 원 단위 정수이므로
그것을 백만원으로 나눠 **숫자 셀**에 넣는다. 붙여넣으면 바로 수식에 들어간다.
Word 경로([D53](#d53))가 렌더된 텍스트를 읽는 것과 대비된다 — 목적이 다르면
읽는 곳도 다르다.

```
요약 · 손익계산서 · 재무상태표 · 현금흐름표 · 부문 · 지표·추정 · 수치 출처

[손익계산서]
  항목      2023    2024     2025      2026     단위
  매출액   8,892,412  10,294,103  11,314,459  12,766,943  백만원
  영업이익   660,544     735,006     913,331   1,030,579  백만원
```

**「수치 출처」 시트가 이 파일의 차별점이다.** 셀 하나하나에 키·산식·데이터셋·
공시번호와 **원문 절로 가는 하이퍼링크**가 붙는다([D36](#d36) · [D44](#d44)).
모델에 붙여 넣고도 되짚을 수 있다 — [Daloopa](https://daloopa.com/benefits/model-updates)가
같은 것을 한다.

**밟은 것 둘**: 연도 머리행에 천단위 구분이 붙어 `2,025`가 됐다. 그리고
비율(`8.1%`)을 백만으로 나누면 `0`이 되므로 단위별로 갈라야 한다.

### D57 — 분기 시계열과 분기 차트: 호출 4번으로 8분기

[D54](#d54)에서 남긴 갭 중 하나. 실제 증권사 리포트는 분기 실적 표를 싣는데
(벤치마크 실측: 22행 × 8분기) 우리에겐 분기축이 아예 없었다.

**DART는 누적만 준다.** 1분기·반기·3분기·사업보고서가 각각
`Q1 / Q1+Q2 / Q1+Q2+Q3 / 연간` 누적이다. 단독 분기는 빼서 만든다.

**그리고 각 보고서가 전년 동기 누적을 함께 준다**(`frmtrm_add_amount`,
[D44](#d44)). 그래서 **한 해 4건만 받으면 당기 4분기 + 전년 4분기 = 8분기**가
나온다. 8번 부를 필요가 없다 — 실측 삼성전기 **1.6초**.

```
| 항목   | 1Q24 | 2Q24 | 3Q24 | 4Q24 | 1Q25 | 2Q25 | 3Q25 | 4Q25 |
| 매출액  | 2.61조 | 2.57조 | 2.62조 | 2.49조 | 2.74조 | 2.78조 | 2.89조 | 2.90조 |
| 영업이익 | 1,836억 | 2,115억 | 2,249억 | 1,150억 | 2,005억 | 2,130억 | 2,603억 | 2,395억 |
```

**한 칸이라도 비면 그 분기를 만들지 않는다.** 뺄셈은 두 값이 다 있어야
성립한다 — 반기보고서가 아직 안 나온 해에 3분기를 지어내면 거짓이 된다.
**분기가 음수여도 버리지 않는다.** 4분기에 비용을 몰아 넣으면 실제로 그렇다.

#### 차트 둘 — 동료가 꼽은 업무 카테고리

[D55](#d55)의 동료 인풋에 **「리포트 내에 차트 그리기」**가 업무 카테고리로
있었다. 조사 문서에 없던 항목이고, 우리는 부문 구성·연간 추이 두 종뿐이었다.

* **분기 막대** — **음수를 아래로 그린다.** 전부 위로 그리면 적자 분기가
  흑자처럼 보인다. 0선은 음수가 있을 때만 긋는다. 최근 4개 분기를 진하게.
* **이익률 선** — **비율은 막대가 아니라 선이다.** 크기가 아니라 수준이라,
  막대로 그리면 8%와 9%가 거의 같아 보인다.

빈 분기는 **0으로 그리지 않고 건너뛴다** — 0으로 그리면 실적이 사라진 것처럼
보인다.

#### 밟은 것 — 템플릿 `for`로 표를 돌리면 한 줄로 붙는다

`trim_blocks`가 블록 태그 뒤 개행을 먹어 표 전체가 한 줄이 됐다(템플릿 머리
주석이 경고하던 그 함정이다). **열 수가 가변인 표는 파이썬이 만들어 통째로
넘긴다** — `sensitivity_table`이 이미 그렇게 하고 있었다.

### D58 — 코퍼스 집계: 「글보다 표」는 맞았지만 방향이 반대였다

982편을 훑어 표를 세었다(`scripts/table_inventory.py` → `corpus/table_inventory.json`).

| | 편수 | 표 비중 | 표 개수 | 쪽수 | **분기축 보유** |
|---|---|---|---|---|---|
| 학생(SMIC) | 777 | **34%** | **36개** | **32쪽** | 18% |
| 증권사 | 189 | **49%** | 10개 | **6쪽** | **61%** |
| 증권사(수상) | 10 | 45% | 8개 | 5쪽 | **80%** |

**학생 리포트가 표는 더 많다(36개).** 다만 32쪽에 흩어져 있고, 증권사는
6쪽에 10개로 밀도가 높다. 차이는 「표를 더 넣어라」가 아니라 **「6쪽 안에
끝내라」**다.

**분기축이 갈랐다** — 증권사 61%, 수상작 80% vs 학생 18%.
[D57](#d57)에서 붙인 것이 정확히 그것이다.

#### 증권사만 쓰는 행 라벨

```
영업이익률   28% (학생 5%)      세전이익     20% (학생 0%)
구분        25% (학생 5%)      지배주주순이익 20% (학생 0%)
목표주가     14% (학생 0%)

안정성/유동비율/부채비율/순차입금       9% (학생 0%)
수익성/ROA/ROE/EBITDA마진          9% (학생 0%)
성장성/매출액/영업이익/EBITDA         9% (학생 0%)
```

마지막 셋이 「주요 투자지표」 표의 3블록이다. 우리 상태:

| 블록 | 상태 |
|---|---|
| 성장성 | **있음** |
| 수익성 | ROE 있음, **EBITDA 막힘** ([D54](#d54): CF 요약본에 감가상각비 없음) |
| 안정성 | **유동비율·부채비율 추가** ← 이 결정 |
| 목표주가·상승여력 | **안 함** ([D4](#d4), 의도적) |

#### 안정성 — 유동비율과 부채비율만

```
삼성전기  유동비율 185.8% · 부채비율 49.0%
삼성물산  유동비율 154.0% · 부채비율 50.5%
```

**순차입금은 안 낸다.** 차입금 계정명이 회사마다 다르다 — 삼성전기는
`유동성장기차입금`·`단기차입금`·`장기차입금`, 삼성물산은 `단기차입금`·
`사채 및 장기차입금`. 이름 매칭으로 합산하면 **놓친 계정만큼 부채가 적어
보이는 방향으로** 틀린다. 틀린 순차입금은 없느니만 못하다.

#### 이 집계가 남기는 것

* **분량**: 우리 노트는 증권사(6쪽)보다 길 것이다. 압축이 다음 과제다
* **EBITDA**: 「수익성」 블록을 채우려면 감가상각비가 필요한데 DART 요약
  현금흐름표에 없다. 부문 주석 합계가 유일한 경로다([D33 보강](#d33-2))
* **순차입금**: 차입금 계정 매핑을 제대로 하면 열린다

### D59 — 순차입금: 못 만든다고 했다가, 구성을 보여주는 방식으로 만들었다

[D58](#d58)에서 *"틀린 순차입금은 없느니만 못하다"*며 뺐다. 차입금은 표준계정
코드가 없어 이름으로 모을 수밖에 없고, 놓치면 **부채가 적어 보이는 방향으로**
틀리기 때문이다.

**빠뜨린 선택지가 있었다 — 무엇을 더했는지 보여주면 된다.**

```
차입금  3개 계정 합산
  유동성장기차입금        0억원
  단기차입금          2조 34억원
  장기차입금          1,884억원
```

계정명이 회사마다 다른 것은 사실이다(실측 5사): 삼성전기 `유동성장기차입금`·
`단기차입금`·`장기차입금` / 삼성물산 `사채 및 장기차입금` / 파마리서치
`유동성전환사채`. 하지만 **합산 결과를 숨기지 않고 구성 계정을 단계에 내면**
빠진 것이 있는지 사람이 본다. 「검산할 수 없으니 안 만든다」와 「검산할 수
있게 만든다」는 다르다.

```
삼성전기   총차입금 2조 1,918억 · 순차입금 -5,094억 · 순차입금비율 -5.2%
파마리서치  총차입금    84억 · 순차입금 -1,672억 · 순차입금비율 -23.1%
```

둘 다 음수 — 순현금이다. 부호를 뒤집어 「순현금」으로 쓰지 않는다. 값이
음수라는 사실이 곧 정보다.

#### 밟은 것 — 레지스트리가 중복을 막았다

부채비율을 `metrics.py`에 만들었는데 `valuation.py`가 이미
`debt_ratio_{y}a`로 등록하고 있었다. 레지스트리가 **키 중복으로 거부**했다:

```
ValueError: key 중복 등록: 'debt_ratio_2025a'
            (기존 48.978% / 신규 48.978%). 한 수치는 하나의 원천만 가져야 한다.
```

**값이 같은데도 막는 것이 옳다.** 두 곳에서 만들면 한쪽 산식이 바뀔 때 조용히
갈라진다. 불변식이 제 일을 했다.

### D60 — KRX 시세가 열렸다 (Encoding 키 함정) · 전사 EBITDA

#### `Q7`이 풀렸다 — 다만 키 형태 때문에 한 번 튕겼다

`KRX_API_KEY`(공공데이터포털 「금융위원회_주식시세정보」)가 들어왔다.
첫 호출은 **403 `SERVICE_KEY_IS_NOT_REGISTERED_ERROR`**였다.

원인은 키가 **Encoding 형태**였던 것이다. data.go.kr은 인증키를 두 가지로
준다 — Encoding(`%2F` 등이 박힌 것)과 Decoding. `httpx`가 params를 다시
인코딩하므로 Encoding 키는 `%`가 `%25`가 되어 서버가 못 알아본다.

```
[원본(Encoding)] HTTP 403 — 등록되지 않은 서비스키
[디코딩]         HTTP 200 — NORMAL SERVICE
```

**어느 쪽을 넣어도 되게 받는 쪽에서 푼다.** 「Decoding 키를 쓰십시오」라고
문서에 적어 두는 것보다, `%`가 있으면 `unquote`하는 편이 낫다 — 사람이
어느 키를 복사했는지 기억하게 만들 이유가 없다.

실측: 삼성전자 254,000원 · 삼성전기 1,325,000원 · 파마리서치 370,000원
(2026-07-27 종가).

**아직 파이프라인에 안 붙였다.** 지금 밸류에이션은 배당에서 역산한 주가를
쓴다([D19](#d19)). 실제 종가로 바꾸면 PER·PBR·시가총액의 의미가 달라지고
노트 문구도 따라 바뀌어야 한다 — 세션 끝에 서두를 일이 아니다.

#### 전사 EBITDA — 부문 주석이 유일한 경로

[D54](#d54)에서 막혔던 것. DART 요약 현금흐름표에 감가상각비 조정 항목이
없어서(삼성전기 CF 30계정에 상각 0건) 전사 EBITDA를 못 만들었다. 부문
주석에서 뽑은 **부문별 감가상각비**([D33 보강](#d33-2))를 합치면 된다.

**전 부문에 감가상각비가 있을 때만 만든다.** 하나라도 빠지면 EBITDA가
과소계상되고, 그건 회사가 실제보다 비싸 보이게 만든다.

```
삼성전기   EBITDA 1조 8,177억원
삼성물산   EBITDA 4조 3,511억원
파마리서치  없음 (부문 손익 미공시 — 정상 부재)
```

이로써 코퍼스 집계([D58](#d58))가 가리킨 「주요 투자지표」 3블록 중
**성장성·수익성·안정성이 모두 채워졌다.**

### D61 — 실제 종가를 쓴다. 역산 앵커는 **중앙값 −32.9%** 어긋났다

[D19](#d19)는 시세가 없어 **배당에서 주가를 역산**했다 —
`주가 = 주당현금배당금 / 현금배당수익률`. 「시세 어댑터가 붙으면 대체한다」고
적어 두고 [Q7](#열린-질문)로 남겨 뒀다: *역산 앵커와 실제 종가의 괴리가
얼마인가.*

키가 들어왔고([D60](#d60)) 재봤다:

| 종목 | 실제 종가 (2026-08-05) | 역산 대비 | PER | PBR |
|---|---|---|---|---|
| 삼성전기 | 1,356,000원 | **−80.7%** | 145.1배 | 11.03배 |
| SK하이닉스 | 1,668,000원 | −55.0% | 26.9배 | 10.08배 |
| 삼성전자 | 246,000원 | −54.8% | 37.2배 | 3.91배 |
| 삼성물산 | 347,500원 | −32.9% | 23.3배 | 1.19배 |
| HMM | 21,100원 | −2.4% | 10.8배 | 0.75배 |
| 파마리서치 | 378,000원 | **+8.8%** | 23.8배 | 6.34배 |

**중앙값 −32.9% · 범위 −80.7% ~ +8.8%.** 역산 앵커는 밸류에이션에 쓸 수 있는
값이 아니었다. 배당수익률이 회계연도 전체를 뭉갠 값이라 그렇다 — 주가가
크게 오른 종목일수록 역산이 낮게 나온다(삼성전기 −80.7%).

**Q7 해소.** 이제 시세가 있으면 그것을 쓰고, 없으면 역산으로 물러난다 —
키가 없는 환경에서도 노트는 나와야 한다. **역산값은 버리지 않고 괴리를 재서
남긴다**(`implied_gap_pct`).

**어느 날 종가인지 밝힌다.** 헤더에 `주가 (2026-08-05)`, 작성 기준에
*"주가는 2026-08-05 종가(금융위 주식시세정보)이며 … 실적은 사업연도 기준이라
두 시점이 다르다"*. 날짜 없는 PER은 검증할 수 없다.

#### 밟은 것 — 시세를 최신순으로 받아 가장 오래된 값을 썼다

`get_prices()`가 API 응답 순서(최신순)를 그대로 돌려줬다. 부르는 쪽은
`points[-1]`을 최신으로 알고 집었다 — **08-05 대신 07-20 종가를 썼다.**
어댑터가 날짜순으로 세워서 돌려준다.

### D62 — 엑셀 모델에 채워 넣는다. **수식은 건드리지 않는다**

[D55](#d55)의 목표. RA 업무의 중심에 모델 관리가 있고, 새 공시가 나오면 그
숫자를 모델에 옮겨 적는 것이 반복 노동이다. 우리는 그 숫자를 **검산까지 마친
채로** 갖고 있다. [Daloopa](https://daloopa.com/benefits/model-updates)가
하는 일 — **모델을 대체하지 않고 먹인다.**

#### 남의 파일에 쓰는 일이다 — 안전 규칙 넷

1. **수식 셀은 절대 건드리지 않는다.** 값이 `=`로 시작하면 손대지 않는다.
   RA의 모델은 수식 덩어리이고, 하나 깨뜨리면 그 사람 하루가 날아간다.
2. **원본을 고치지 않는다.** 사본을 만들어 준다.
3. **무엇을 어디에 썼는지 전부 돌려준다.** 시트·셀·이전/이후 값을 목록으로.
   파일만 주면 무엇이 바뀌었는지 알 수 없다.
4. **모르면 안 쓴다.** 라벨이 확실히 안 맞으면 건너뛰고 이유를 남긴다.

넷 다 테스트로 잠갔다(`tests/test_model_fill.py` 13건).

#### 먼저 확인한 것 — 왕복해도 안 깨지나

`openpyxl`로 열고 다시 저장하면 **수식·번호서식·차트·조건부서식·틀고정이
모두 보존**된다(실측). 이게 안 되면 이 기능 자체가 성립하지 않으므로
**만들기 전에 확인했다.**

#### 관통 실측

```
채움 14칸 · 건너뜀 1칸
  ✓ 손익!D2  매출액   2025 → 11,314
  ✓ 손익!D5  영업이익  2025 →    913
  ✗ 손익!D4  매출총이익      — 수식이 있어 건너뜀
수식 보존: '=D2-D3'
```

**찾는 방법**: 열 머리행에서 연도를 읽고(`2025A` · `FY25` · `25F`), 왼쪽
세 열에서 행 라벨을 읽는다. 하우스마다 표기가 달라(`매출액` · `매출` ·
`Revenue` · `매출액(십억원)`) 별칭을 두고 단위·괄호·공백을 떼어 맞춘다.
**단위는 사람이 고른다** — 십억원/백만원/억원/원. 모델의 단위를 우리가
추측하면 1000배 틀린 숫자가 들어간다.

#### 아직 아닌 것

* **매핑을 기억하지 않는다.** 다음 분기에 같은 모델을 올리면 다시 찾는다.
  한 번 확인한 매핑을 카드에 저장하면 되지만, 먼저 실제 모델로 몇 번
  돌려보고 정하는 편이 낫다.
* **추정 열은 안 채운다.** 실적만 넣는다 — 추정은 그 사람의 판단이다.
* `.xls`(구형)는 안 받는다.

### D63 — 헤더는 줄마다 따로 확인한다 (D61 회귀)

한화비전 분기 카드가 **`unknown_placeholder`**로 막혔다:

```
레지스트리에 없는 key 참조: {{num:market_cap_2026a}}
```

헤더가 「주가 앵커가 있으면」 시가총액과 주가 **두 줄을 함께** 냈다. 전에는
그게 맞았다 — 주가가 배당 공시에서 왔고 주식수도 **같은 공시**에 있었기
때문이다.

[D61](#d61)에서 주가 출처를 시세로 옮기면서 그 전제가 깨졌다. **시세는
독립적으로 온다.** 분기보고서는 주식수·배당 6종이 아예 없으므로([D52](#d52))
**종가는 있는데 발행주식수가 없어** 시가총액을 계산할 수 없다. 그런데 헤더는
여전히 두 줄을 냈다.

**줄마다 레지스트리에 있는지 확인한다.** 「주가가 있으면 시가총액도 있다」는
더 이상 참이 아니다.

```
분기: | 주가 (2026-08-05) | 49,000원 |          ← 시가총액 줄 없음
연간: | 시가총액 | 105조 2,265억원 |
      | 주가 (2026-08-05) | 1,356,000원 |
```

**게이트가 잡아 준 것이다.** 본문이 없는 수치를 참조하면 발간이 막힌다 —
그게 없었으면 헤더에 `{{num:market_cap_2026a}}`가 그대로 박힌 노트가
나갔을 것이다. 불변식이 두 번째로 제 일을 했다([D59](#d59)의 키 중복에 이어).

### D64 — 「얼마가」가 아니라 **「무엇이」** 달라졌는가

*"기존 보고서 대비 어떤 영역이 어떻게 달라졌는지 비교해서 보여줘야 하는 거
아닌가 싶기는 함"*

맞다. [D46](#d46)의 비교는 **숫자만** 냈다:

```
매출액 (2026E)   10조 3,730억원 → 12조 6,537억원   +22.0%
```

이건 「얼마가 달라졌나」다. RA가 새 분기 노트를 열고 처음 묻는 것은
**「내가 지난번에 본 그림이 아직 맞나」**다.

**영역별 대조를 붙였다.** 올린 직전 리포트가 본 그림을 이번 공시와 맞춰
보고, 넷 중 하나로 판정한다 — `유지` · `강화` · `약화` · `확인불가`.

실측(키움 한화비전 리포트를 올려 2026 1분기와 대조):

```
[약화]   실적 추이
  직전  외형 성장과 함께 영업이익 개선세가 이어지고 하반기도 긍정적으로 보았다
  지금  영업이익이 증가했지만 매출 증가보다 느려 비용 부담이 외형보다 빠르게 커졌다

[약화]   수익성
  직전  시큐리티 가격 인상과 산업용장비 매출 인식으로 수익성 개선을 보았다
  지금  영업이익률이 악화됐고 원가율과 판관비율만으로 설명하기 어렵다

[확인불가] 성장 동력
  직전  에스엠티·티씨본더, 특히 에이치비엠 관련 장비 수요를 성장 동력으로 제시했다
  지금  이번 공시만으로는 해당 수요와 시장 성장 전망을 확인할 수 없다
```

#### 「확인불가」를 두려워하지 않는다

다섯 영역 중 셋이 `확인불가`로 나왔다. **그게 맞다.** 직전 리포트의 핵심
논거(HBM 시장 성장성·목표주가 근거)는 공시 밖에 있고, 우리는 공시만 읽는다.
「모르는 것을 모른다고 하는 것」이 이 제품의 값이다 — 억지로 판정하면
[D31](#d31)이 막아 온 것을 우회하는 셈이다.

#### 숫자는 여기에도 안 들어간다

* 프롬프트에 넣기 전 직전 리포트의 숫자를 `mask_numbers()`로 가린다
  ([D45](#d45)와 같은 규칙)
* 나온 문장에 숫자가 하나라도 있으면 **그 영역을 버린다**
* 「늘었다/줄었다/유지됐다/뒤집혔다」로 쓰게 한다

직전 리포트의 숫자는 우리가 검산하지 않았고([D48](#d48)), 이번 공시 숫자는
표에 이미 있다. 여기서 숫자를 쓰면 **검산 안 된 값이 검산된 것처럼 섞인다.**

**두 층으로 낸다**: 숫자 층([D46](#d46)의 추정 diff)과 영역 층(이것).
앞은 정확하고, 뒤는 읽힌다.

### D65 — 서버가 **항상 완전한 ViewModel**을 준다

카드를 열면 브라우저가 「This page couldn't load」를 띄웠다. **두 번째다**
([D63](#d63)에 이어).

원인은 같은 종류다. 카드는 **만들어진 시점의 `vm`을 그대로** 들고 있는데,
그 뒤에 필드를 추가하면 옛 카드에는 그 필드가 없다. 화면이 `vm.areas.length`를
읽으면 `undefined.length` → TypeError → React가 트리 전체를 내린다.

```
vm 필드 유무 (D64 이전에 만든 카드):
   areas          ★ 없음
   changes        있음
   stages         있음
```

**필드를 추가할 때마다 화면에 `?.`를 하나씩 다는 것은 못 지킨다.** 오늘만
`vm.changes`·`vm.quarter_chart`·`vm.segment_items`·`vm.areas` 넷을 추가했고,
그때마다 옛 카드가 깨질 수 있었다. 개별 방어는 언젠가 빠뜨린다.

**그래서 규칙을 서버로 옮겼다**: 카드를 내보낼 때 지금 `ViewModel`의 빈
기본값을 채워서 준다. 저장된 값이 이기고, 없는 것만 채운다.

```python
full = dataclasses.asdict(ViewModel(symbol="", year=0))
return {**full, **vm}
```

**빈 `vm`은 그대로 둔다.** 생성 중인 카드는 `vm`이 `{}`이고, 화면이 그걸로
「아직 안 됐다」를 안다([D63](#d63)의 `ready`). 거기에 기본값을 채우면
빈 노트를 다 만들어진 것처럼 그린다.

### D66 — 텔레그램: **수집기를 갈아끼울 수 있게** 만든다

[10](research/10-prism-insight-and-scope.md) §4에서 *"사용자가 내보낸 것을
올린다"*로 정했는데, 실제 구독 화면을 보고 흔들렸다 — **채널 34개, 미읽음이
채널당 수백~8,638건**이다. 매일 손으로 내보낼 사람은 없다.

그래서 네 경로를 다 재보고 다시 정했다.

| 경로 | 되는가 | 약관 | 자동화 |
|---|---|---|---|
| 전체 내보내기 | **공개 채널은 내 글만** | 안전 | 불가 |
| **채널별 내보내기** | **공개·비공개 전체 이력** | 안전 | 불가 |
| Bot API | 사실상 불가 (관리자만 추가, 히스토리 없음) | — | — |
| MTProto (Telethon) | 전부 · 실시간 | **정면 위반** | 완전 |
| t.me/s/ | 공개+미리보기만 | 스크래핑 조항 | 가능 |

**두 가지가 문서에 안 나와 있어 소스를 봐야 나왔다.**

1. **전체 내보내기와 채널별 내보내기가 다르다.** 스키마 문서는 *"public
   channel exports will only contain messages sent by the user"*라고 하지만
   그건 **전체 내보내기 얘기**다(`export_view_settings.cpp:777`이 체크박스를
   강제로 켠다). 채널별은 `export_controller.cpp:23`의 `NormalizeSettings()`가
   단일 채널이면 마스크를 전체로 덮어쓴다 — **채널 종류 무관 전체 이력**
2. **막히는 조건이 있다.** `data_peer.cpp:789`의 `canExportChatHistory()`가
   `!allowsForwarding()`이면 false다. 관리자가 「콘텐츠 저장 제한」을 켜면
   **메뉴 자체가 사라진다.** 유료 채널은 켤 이유가 충분하다

**Telethon을 막는 것은 계정 정지가 아니라 약관이다.** [Content
Licensing](https://telegram.org/tos/content-licensing)이 *"…or **deployment**
of artificial intelligence, machine learning models"*를 금지하고, 예외를
*"non-global **context window**"* 단위 동의로 한정한다. **텔레그램이 LLM
컨텍스트 투입을 명시적으로 사정거리에 넣었다.** 「학습만 금지, 추론은 허용」
해석이 성립하지 않는다. 증권사 납품물에 들어가면 컴플라이언스에서 막힌다.

**그런데 볼륨 문제는 생각보다 작았다.** 미읽음이 큰 채널이 정확히 **이미 더
나은 출처로 갖고 있는 것들**이다:

| 채널 | 미읽음 | 우리가 이미 가진 것 |
|---|---|---|
| News Feed 🇰🇷(ko) | 8,638 | 네이버 뉴스 API |
| 실시간 속보 단독 뉴스 | 1,428 | 〃 |
| AWAKE 52주 신고가 | 777 | KRX 주가 |
| AWAKE 실시간 공시 · 주요공시 알리미 | 298 | **DART 직접**(원문 절까지 링크) |

**약 11,000건 중 대부분이 중복이다.** 텔레그램에만 있는 것은 애널리스트
코멘트·비공식 리서치·종토방 센티고, 그건 수동 내보내기로 감당된다.

**그래서 결정**: 파서·집계는 하나로 두고 **수집기만 갈아끼운다.**
납품본은 업로드, 개인 사용은 각자 판단. 리스크가 코드가 아니라 **배포
경계**에 놓인다.

**부수 사실 셋** (설계에 바로 영향):
- **`text`가 아니라 `text_entities`를 쓴다.** `text`는 서식이 있으면 문자열
  대신 배열이 되어 분기가 생긴다
- **조회수(`views`)가 내보내기에 없다.** 중요도를 조회수로 매길 수 없다.
  `reactions`는 들어온다
- **공개 채널은 username이 없어 딥링크를 못 만든다.** 비공개는
  `t.me/c/{id}/{msg_id}`로 조립된다

**그리고 텔레그램은 문서 레인이 아니라 [D45](#d45) 기사 레인이다.** 건물
안에서 가장 검증 안 된 숫자다. 맥락·단서로는 되고, 본문 수치의 출처로는
절대 안 된다.

### D67 — 종목별 수급은 **우리가 조달할 수 없다**. 어댑터 자리다

[10](research/10-prism-insight-and-scope.md) §5에서 3순위로 둔 것인데,
실제로 호출해 보니 전제가 틀렸다.

| 데이터 | 프로그램 수신 | **재배포** |
|---|---|---|
| 종목별 신용잔고/융자/대주 | 증권사 OpenAPI만 | **불가** |
| 종목별 투자자별 순매수 | KRX 로그인 / 증권사 API | **불가** |
| 공매도 거래·잔고 | 〃 | **불가** |
| **시장 전체** 신용공여 잔고 | **data.go.kr, 지금 키** | **가능** |

**종목별 신용잔고는 KRX가 아예 공표하지 않는다.** Data Marketplace 메뉴를
전수 확인했다 — 공매도·투자자별·대차는 있고 신용은 `신용등급`(회사채
평가)뿐이다. **RA에게 그 요청이 오는 이유가 바로 이것이다.**

**KRX 스크래핑 경로는 2025-12-27부로 죽었다.** pykrx가 쓰던
`getJsonData.cmd`에 3종을 던지면 전부 `LOGOUT`이다(전종목 시세·투자자별
거래실적·공매도 통계). Data Marketplace 개편으로 로그인이 필수가 됐고
pykrx도 `KRX_ID`/`KRX_PW`를 요구하도록 바뀌었다.

**종목별을 실제로 주는 곳은 증권사 OpenAPI뿐인데 약관이 막는다.** KIS의
`daily-credit-balance`(TR `FHPST04760000`)는 필드가 RA 요청과 일대일로
맞는다(`whol_loan_rmnd_stcn`·`whol_loan_rmnd_amt`·`whol_loan_gvrt`). 그러나
*"계좌를 보유한 **개인 고객**이 자기 자산의 투자 목적에 한해… **제3자 제공은
불가**"*, *"**법인 고객**은 코스콤 등과 별도 시세정보이용계약을 반드시 체결"*.

**그래서 자리가 바뀐다. 우리는 데이터 공급자가 아니라 어댑터다.** RA가 속한
증권사는 이미 코스콤/KRX 라이선스를 갖고 있다. 없애야 할 것은 데이터가
아니라 **「뽑아서 정리하는 시간」**이다.

**지금 열 수 있는 것 하나** — `금융위원회_금융투자협회종합통계정보`
(data.go.kr, 무료·자동승인, **이용허락범위 제한 없음** = 재배포 안전):

```
apis.data.go.kr/1160100/service/GetKofiaStatisticsInfoService/getGrantingOfCreditBalanceInfo
```

**진단 방법을 기록해 둔다** — 미등록이면 `403
SERVICE_KEY_IS_NOT_REGISTERED_ERROR`, 없는 오퍼레이션이면 `400
NO_OPENAPI_SERVICE_ERROR`다. **403은 「엔드포인트는 실재하고 키만 미등록」**을
뜻한다. 그리고 data.go.kr **영문 페이지의 오퍼레이션명은 틀렸다**(번역된
가짜 이름) — HTML에서 직접 긁은 실명을 써야 한다.

단, **시장 전체 합계**지 종목별이 아니다. 한계를 명시해야 한다.

### D69 — OpenDART가 **IP를 끊었다.** 한도가 아니라 **요청률**이다

피어 조사 중 「KSIC로 피어를 뽑을 수 있는가」를 실측하려고 전 상장사
3,981곳의 `company.json`을 훑었다. 6워커로 병렬 호출하자 **OpenDART가 IP를
끊었다** — 그 뒤 `corpCode.xml`까지 TCP 연결이 거부(curl `HTTP 000`)됐고
40분 넘게 안 풀렸다. 같은 회선에서 금융위 시세 API와 일반 인터넷은 정상이라
**DART만 막힌 것**이 확인됐다.

**일 20,000건 한도는 20%도 안 썼다.** 한도와 별개로 순간 요청률에 WAF가 있다.
순차 호출은 실측 0.082초/건으로 멀쩡했는데 병렬로 바꾼 순간 막혔다.

**그리고 우리 코드가 차단을 증폭시켰다.** `_request`가
`httpx.TransportError`를 재시도 대상으로 잡는데, 연결 거부(`ConnectError`)와
프로토콜 오류(`RemoteProtocolError`)가 **전부 그 하위 클래스**다. 즉 막힌
뒤에도 `1초 → 2초 → 4초`로 4번씩 더 두드렸다. 6워커 × 4회 = 가장 두드리면
안 될 때 가장 세게 두드리는 구조였다.

**고친 것 셋** (`kr/dart.py`):

| | 전 | 후 |
|---|---|---|
| 전송 오류 | `max_retries`(3)회 재시도 | `transport_retries`(1)회 뒤 **`DartBlockedError`** — "재시도 말고 기다려라" |
| `corpCode.xml` | **인스턴스 메모리만** | `.arc-store/cache`에 24시간 디스크 캐시 (원자적 쓰기, 깨지면 네트워크로 폴백) |
| 동시성 | 무제한 | `max_connections=2` + 요청 간 **0.25초** |

**디스크 캐시가 셋 중 가장 크다.** 전에는 프로세스가 새로 뜰 때마다 수 MB
zip을 다시 받았다 — 테스트 한 번, 웹 워커 재시작 한 번, CLI 한 번마다.
`web/app.py` 독스트링이 *"corpCode 캐시가 프로세스 메모리에 있어서"*를 D37에서
서버리스를 배제한 **근거로** 삼고 있었는데, 정작 디스크에는 안 남고 있었다.

**핫스팟은 해법이 아니다.** IP를 바꾸면 당장은 되지만 같은 코드를 돌리면 그
IP도 막히고, 통신사 공유 IP(CGNAT)라 **모르는 사람까지 같이 막힌다.** 배포
환경엔 핫스팟이 없다.

**남는 교훈은 조달 설계 쪽이다.** 전 종목 순회가 필요한 설계였다면 이 사고는
구조적이었을 것이다. 그런데 [D68]의 피어 후보는 **전 종목 순회를 하지
않는다** — 시드는 로컬 코퍼스에서, 시세는 금융위 API에서 온다. 그리고 금융위
시세 API는 `basDt`로 부르면 **하루 1콜에 전 종목**이 온다(실측 2026-08-06
기준 `totalCount` **2,872**). 종목축 3,981콜 대신 날짜축 250콜 — **16배 싸다.**
가장 좋은 재시도는 **애초에 적게 부르는 것**이다.

| Q5 | KOSAI 대비 실질 차별화가 유지되는가 | 시범 발행 후 |
| Q15 | **커버 밖 피어 뷰**가 국내 증권사에도 고통인가 — UBS는 커버리지를 홍콩이 정해 구조적 공백이 생겼다. 국내는 스몰캡까지 커버한다 ([09](research/09-what-the-interview-changes.md)) | 다음 인터뷰 |
| ~~Q16~~ | ~~텔레그램 센티를 법적으로 다룰 수 있는가~~ → **과한 걱정이었다.** 유사투자자문은 **대가를 받고 불특정 다수에게 투자 자문**을 하는 것이고, 「무슨 말이 도는지 요약」은 관측이다. 우리는 투자의견을 애초에 안 낸다(D4). **개인 도구·추천 없음·사용자 업로드**를 지키면 된다 ([10](research/10-prism-insight-and-scope.md) §0) | 2026-08-07 |
| Q17 | **리서치 전용 채팅**이 클라이언트 리퀘스트를 실제로 줄이는가 — 하루 10~15건, 시간 청구 | 만들어 보고 RA에게 |
| Q18 | **신용잔고 요청을 받으면 RA는 실제로 어디서 뽑는가** — 코스콤 CHECK인가, 사내 DB인가, 데이터가이드인가. [D67](#d67)이 우리를 어댑터 자리로 밀었는데 **어느 단자에 꽂는지**를 모른다 | 다음 인터뷰 (SK증권) |
| Q19 | 구독 중인 채널에 **「콘텐츠 저장 제한」이 켜져 있는가** — 켜져 있으면 내보내기 메뉴가 아예 없다([D66](#d66)). 유료 채널일수록 켤 이유가 있다 | RA가 ⋮ 메뉴를 열어 보면 즉시 |
